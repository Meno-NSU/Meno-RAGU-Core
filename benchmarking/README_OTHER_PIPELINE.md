# Проверка другого RAG-стенда на том же наборе вопросов

Этот документ — задание разработчику независимого стенда. Он задаёт общий
протокол сравнения, сохраняя собственную реализацию поиска и подготовки ответа.
Проверка состоит из двух раздельных проходов: сначала ответы и доказательства,
затем оценка неизменяемой выгрузки судьёй. Первый проход судью не вызывает;
второй не обращается к стенду и не повторяет поиск или генерацию ответа.

## 1. Набор данных и идентификаторы

Используйте [data/benchmark_1000_verified.json](data/benchmark_1000_verified.json)
без изменения исходных байтов. В файле **954**, а не 1000 записей.
Каждая запись содержит непустые строки `question` и `ground_truth`.

| Проверка | Ожидаемое значение |
| --- | --- |
| Размер | 777700 байт |
| SHA-256 | `e85bb0b24452372ed2630a568ac91154ec524d4084375a7ac56d94dd04a87aef` |
| Нумерация `index` | С нуля, по порядку исходного массива |

Не исправляйте формулировки и не переводите вопросы или эталоны.
`ground_truth` хранится локально и **не передаётся генератору**, поиску или
переранжированию. На втором проходе он становится полем `reference`.

Идентификатор должен совпадать между стендами и моделями. Его вычисляет
[`load_dataset()` в common.py](common.py). Для независимой реализации:

```python
dataset_sha256 = hashlib.sha256(original_file_bytes).hexdigest()
serialized = json.dumps([dataset_sha256, index, original_row], ensure_ascii=False,
                        sort_keys=True, separators=(",", ":"), allow_nan=False)
sample_id = hashlib.sha256(serialized.encode("utf-8")).hexdigest()
```

Здесь `original_row` — исходный объект с `question` и `ground_truth`, до
переименования полей. Имя стенда и модель в `sample_id` не включаются.

## 2. Что оставить собственным, а что зафиксировать

Стенд сохраняет свой поиск, разбиение документов, модель векторных представлений,
переранкер, сборку контекста и промпты. BGE-M3 из раздела оценки обязателен
только для соответствующей метрики RAGAS, а не для поиска другого стенда.
Не добавляйте переписывание или LLM-переранжирование, если таких этапов нет.

Чтобы оценить различие именно конвейеров, используйте одинаковый снимок корпуса
с одинаковыми датами и составом документов. Запишите его контрольные суммы.
Если корпуса различаются, обозначьте результат как сравнение полных систем;
приписывать разницу только алгоритму поиска или генератору нельзя.

Каждый вопрос запускается независимо, без истории и сохранённого состояния
предыдущих вопросов. Проведите два варианта: с Meno Lite и с Gemma.
Выбранная генеративная модель используется во всех существующих генеративных
этапах варианта. Специализированные модели поиска и оценки остаются собственными.
Если необходимо сохранить отдельные вспомогательные LLM, перечислите их
в конфигурации и обозначьте сравнение полных систем с разным составом моделей.

## 3. Службы моделей и порядок доступа

| Назначение | Имя API | Адрес | Окно |
| --- | --- | --- | ---: |
| Генератор 1 | `meno-lite`, Meno Lite 0.1 | `http://127.0.0.1:9020/v1` | 16384 |
| Генератор 2 | `gemma-4-12B-it` | `http://everest.nsu.ru:9022/v1` в фазе сбора | 60000 |
| Судья | `qwen3.8-27b` | `http://everest.nsu.ru:9022/v1` в фазе оценки | 32768 |
| Векторы RAGAS | `BAAI/bge-m3` | `http://127.0.0.1:8001/v1` на meno | — |

`127.0.0.1` относится к машине, где выполняется запрос. Эти адреса подходят
при запуске на meno; с другой машины нужен согласованный сетевой адрес или
туннель. Фактические адреса указываются настройками вашего сборщика.

**Сейчас Everest занят судейским проходом.** Gemma и судья используют один
порт в разные фазы. Не заменяйте работающего судью ради нового первого прохода.
Восстановление Gemma планируется после завершения текущих запусков либо
предоставляется другой endpoint с теми же весами и нужным окном.
Перед запуском проверьте имя модели через `/v1/models` и сохраните ответ.

## 4. Первый проход: параметры и сохранение ответа

В каждом варианте передавайте только исходный вопрос, без эталона.
Для финального генератора запросите `temperature=0`, `max_tokens=4096`,
`seed=42`, если служба поддерживает seed. Сохраните как запрошенные, так и
фактически применённые параметры: промежуточный сервер может менять лимит.
Неподдерживаемый seed явно отметьте; не объявляйте такой запуск побайтово
воспроизводимым. Предел входа и ответа должен соответствовать окну модели.

Для совпадающих по назначению генеративных этапов условия сравнения следующие:

| Этап, если он уже есть | Параметры |
| --- | --- |
| Переписывание вопроса | temperature 0.1, max_tokens 1024, seed 42 |
| Классификационное LLM-переранжирование | temperature 0, max_tokens 1, logprobs=true, top_logprobs=5, метки 0/1/2 |
| Резервная JSON-классификация, если используется | temperature 0, max_tokens 20 |

В LLM-переранжирование передаётся `enable_thinking=false`, seed там не задаётся.
Для переписывания и финального ответа reasoning явно не переключается:
сохраните настройку сервера и chat template. Если собственный этап устроен
иначе и параметры неприменимы, зафиксируйте различие, сохранив его реализацию.
Таблица не требует добавлять отсутствующий этап или менять тип переранкера.

Для сопоставимого режима сбора лимиты — 1 полный запрос Meno Lite и 8 Gemma.
Очереди можно выполнять одновременно, когда доступны обе модели. Это лимиты
полных запросов стенда; фактическое число внутренних вызовов может отличаться.
Логируйте начало, завершение, длительность, попытку и причину ошибки вопроса.

## 5. Нейтральная выгрузка первого прохода

Одна успешная запись JSONL соответствует ключу `(pipeline_id, model, sample_id)`.
`pipeline_id` — выбранное вами неизменяемое имя версии стенда. Например:

```json
{"sample_id":"<64 шестнадцатеричных символа>","index":0,"pipeline_id":"other-stand-v1","model":"meno-lite","user_input":"<исходный question>","response":"<полный ответ>","reference":"<исходный ground_truth>","retrieved_contexts":["<первый фактический блок>","<второй фактический блок>"]}
```

Это схема, а не готовый пример для оценки. Строки заменяются исходными данными
и результатами стенда; `sample_id` вычисляется по правилу раздела 1.
`retrieved_contexts` — упорядоченный список **реально переданных генератору**
блоков после переранжирования, сжатия и ограничения бюджета, если они есть.
Сохраняйте текст блоков без дополнительной обработки и в порядке промпта.
Границы блоков тоже должны соответствовать реальному контексту. Разный размер
блоков влияет на context precision; учитывайте это при сравнении и не меняйте
разбиение специально для оценки.
Не подменяйте их всем найденным пулом, ссылками, эталоном или полным промптом
с инструкциями и вопросом. Документ, удалённый из-за окна, в этот список не входит.

Дополнительно сохраните финальные сообщения генератору, происхождение блоков,
переписанные запросы, идентификаторы и оценки кандидатов, фактический
`finish_reason`, usage, длительности, параметры генерации и исходный ответ API.
Эти поля полезны для аудита; отдельная специфическая схема trace не требуется.
API-токены и заголовки Authorization в выгрузку не включайте.

Проверяющий скрипт должен сверять 954 исходных индекса, `sample_id`, вопрос,
эталон, уникальность ключа, непустой ответ и соответствие блоков финальному
промпту. Для совпадения критериев успеха нужны `finish_reason=stop` и непустой
список непустых доказательств. Если доказательств нет, сохраните это как ошибку
первого прохода без подстановки выдуманного контекста.
Обрезанный ответ (`finish_reason=length`) помечайте ошибкой, а не успехом.
Ошибки храните отдельно со статусом, причиной и числом попыток.
Зафиксируйте SHA-256 готовой выгрузки; после начала оценки её не дополняют.

## 6. Второй проход: общий судья и RAGAS

Используйте **RAGAS 0.4.3** с теми же зависимостями из
[`pyproject.toml`](pyproject.toml) и [`uv.lock`](uv.lock), Python не ниже 3.12.
Не устанавливайте произвольную последнюю версию библиотеки.
Судья: Qwen3.8-27B, alias `qwen3.8-27b`, метка версии `qwen3.8-27b-fp8-v1`.
Зафиксированный режим службы: H100 80 ГБ, vLLM 0.29.0, FP8, `dtype=half`,
окно 32768, `gpu-memory-utilization=0.8`, `max-num-seqs=25`, `--enforce-eager`.
Это сведения о согласованной службе; этот документ не предлагает её перезапуск.

Запросы судье: temperature 0, top_p 1, max_tokens 4096,
`chat_template_kwargs.enable_thinking=false`; seed явно не задаётся.
Instructor использует `max_retries=2`, OpenAI SDK — `max_retries=0`.
Внешний исполнитель допускает до трёх попыток одной метрики.
Для сопоставимого полного прохода параллелизм — 8 одновременно считаемых метрик,
а не 8 вопросов или 25 последовательностей сервера.

Применяйте стандартные английские промпты и примеры закреплённой версии RAGAS.
Исходные вопросы, ответы, эталоны и доказательства не переводите.
Язык промежуточных утверждений и восстановленных вопросов отдельно не закреплён.

| Имя | Класс | Входы и параметры |
| --- | --- | --- |
| `faithfulness` | `Faithfulness` | user_input, response, retrieved_contexts |
| `factual_correctness` | `FactualCorrectness` | response, reference; mode=f1, atomicity=low, coverage=low, beta=1 |
| `answer_relevancy` | `AnswerRelevancy` | user_input, response; strictness=3; векторы BGE-M3 |
| `context_precision` | `ContextPrecisionWithReference` | user_input, reference, retrieved_contexts |
| `context_recall` | `ContextRecall` | user_input, reference, retrieved_contexts |

AnswerRelevancy использует один и тот же BGE-M3 на `8001/v1` у всех стендов.
Передавайте исходные строки без дополнительных инструкций для retrieval-модели.
При temperature 0 три одинаковых последовательных запроса strictness=3
переиспользуют первый кэшированный результат. Это не три независимых суждения.
Сохраняйте такое же кэширование и учитывайте эту оговорку при интерпретации.
Context precision оценивает порядок эффективных доказательств, context recall —
покрытие эталона ими; это не recall по размеченным идентификаторам документов.

Проверяйте готовый запрос судье после добавления схемы Instructor через
`/tokenize`: вход + резерв ответа 4096 + запас 32 должны помещаться в окно
не более 32768. При ошибке токенизации или превышении окна сохраняйте ошибку
метрики. Не обрезайте контекст и не генерируйте новые ответы ради её вычисления.

## 7. Что можно переиспользовать из этой директории

[`RagasAdapter` и `RagasConfig`](ragas_adapter.py) принимают перечисленные
нейтральные поля и могут вызываться напрямую из исполнителя другого стенда.
Метод `score(metric_name, row)` асинхронный; адаптер открывается через
асинхронный контекстный менеджер. Он использует HTTP, собственные кэши и
[`judge_budget.py`](judge_budget.py) для проверки окна; локальная GPU ему не нужна.
Укажите `judge_context_tokens=32768`, `disable_thinking=True`, отдельный `cache_dir`
и согласованные адреса в `RagasConfig`. Телеметрия RAGAS отключается адаптером.

[`collect.py`](collect.py) и [`evaluate.py`](evaluate.py) рассчитаны на конкретные
API и каталоги референсной реализации и не являются готовыми командами для
произвольного стенда. Команды с `--input-jsonl` здесь нет. Не требуется
реализовывать чужие API-маршруты, токены, формат trace или схему SQLite.
Разработчик другого стенда реализует свой сборщик, проверку JSONL и исполнитель
оценки с чекпоинтами; адаптер метрик можно использовать без этих обёрток.

## 8. Чекпоинты, отчёт и передача результатов

Первый проход фиксирует успех по `(pipeline_id, model, sample_id)`, второй —
по тому же ключу плюс `metric`. Сохраняйте каждую запись сразу после завершения
атомарно, до перехода к следующей. Допустимы SQLite с WAL или другой журнал,
который однозначно восстанавливает успешные и незавершённые задания.
Повторный запуск пропускает завершённые записи и повторяет только незавершённые
или ошибочные; успешные внутренние вызовы судьи могут браться из кэша.
Два процесса не должны одновременно писать в один каталог эксперимента.

Показывайте завершено/всего, восстановлено из чекпоинта, ошибки, скорость,
прошедшее время и оценку остатка отдельно для моделей и судейских метрик.
Параллелизм, тайм-аут, число попыток и порядок заданий можно менять при
продолжении. Новые веса, эталоны, ответы, корпус, промпты или параметры метрик
требуют новой версии эксперимента; прежние результаты не перезаписываются.

Ошибки, NaN и Inf записываются как `score=null` и исключаются из среднего;
валидный ноль включается. Среднее рассчитывается отдельно по стенду, модели
и метрике с одинаковым весом вопроса, без общего балла из пяти метрик.
`coverage = число успешных оценок / 954`; отдельно показывайте отсутствующие
ответы первого прохода и ошибки судьи. Для парного сравнения используйте
пересечение успешных `sample_id` нужных стендов и моделей по каждой метрике.

Сначала проверьте по одному длинному контексту каждой модели и все пять метрик.
Затем запустите весь набор, сохранив пробные оценки для продолжения. Передайте
JSONL ответов, оценки и ошибки, сводки покрытия, конфигурацию, версии весов,
контрольные суммы корпуса и выгрузок, промпты и сведения о среде исполнения.
