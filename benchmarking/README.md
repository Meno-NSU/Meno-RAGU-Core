# Бенчмарк Meno RAGU

[Манифест NSU v1](MANIFEST.md) описывает фактический состав эксперимента,
параметры моделей, определения метрик и проверенный smoke на 8 ноября 2026 года.
Его машиночитаемая версия — [manifest.json](manifest.json).
Этот README содержит команды запуска и продолжения.

В исходном `data/benchmark_1000_verified.json` находятся 954 пары
`question`/`ground_truth`. Файл сохранён без изменения исходных байтов.
Для каждой модели выполняются 954 независимых диалога с одним вопросом без истории.
Эталонные ответы используются только на втором проходе и не передаются backend.

## Подготовка сервера

Команды выполняются на meno. Модели, Qdrant и готовая база знаний уже должны
работать. Backend использует базу `nsu-ragu` на порту 9007.
Работающий production-backend и фронтенд в этот запуск не входят.

Под root обновите оба репозитория и включите отдельный токен измерений.
`bench-token` сохраняет остальные настройки `.env.backend` и не выводит секрет.
Повторный вызов сохраняет уже существующий токен.

```bash
sudo -i
export PATH="/root/.local/bin:$PATH"
cd /home/rsolikhov/meno_ragu_stand
git pull --ff-only
cd /home/rsolikhov/Meno-Deploy
git pull --ff-only
./scripts/backend.sh bench-token
./scripts/backend.sh up -d --no-deps --build --wait --wait-timeout 1200 core
curl -fsS http://127.0.0.1:9007/readyz
cd /home/rsolikhov/meno_ragu_stand
```

Первый проход устанавливает только HTTP-зависимости в `benchmarking/.venv`.
RAGAS и его дополнительные библиотеки устанавливаются отдельно, перед оценкой.
Основное окружение backend и образ Docker от них не зависят.

Если контейнер core имеет состояние `unhealthy`, сначала проверьте `/readyz`
и `./scripts/backend.sh logs --tail 300 core`. HTTP 503 от защищённой проверки
бенчмарка означает, что конвейер RAG не загрузился; неверный токен получает
HTTP 404. Сообщение `stand_resources_load_failed` в журнале содержит причину
ошибки загрузки. После её устранения потребуется перезапустить core.

## Первый проход — ответы и данные поиска

Сначала выполните серверную проверку `smoke`. Она проверяет `/readyz`, наличие
обеих моделей и по одному полному запросу RAG для каждой. Проверяются непустой
ответ, штатное завершение, полная трассировка, позиции доказательств в контексте
и отпечаток backend. Команда создаёт tmux-сессию, пишет полный журнал и оставляет
оболочку открытой после завершения.

```bash
benchmarking/run_tmux.sh --session meno-bench-smoke \
  --log-file /home/rsolikhov/logs/benchmark-collect.log \
  smoke \
  --backend-env /home/rsolikhov/Meno-Deploy/.env.backend \
  --output-dir /home/rsolikhov/benchmarks/nsu-v1/collection \
  --models meno-lite gemma-4-12B-it \
  --model-revision meno-lite=0.1 \
  --model-revision gemma-4-12B-it=everest-current \
  --model-concurrency meno-lite=1 \
  --model-concurrency gemma-4-12B-it=8

tmux attach -t meno-bench-smoke
```

Отсоединение от tmux — `Ctrl+B`, затем `D`. Сессия принадлежит пользователю,
который запустил команду; при работе под root подключайтесь тоже под root.
Код завершения 0 означает успех всех выбранных вопросов. Итоги пробного запуска
можно проверить без чтения большого журнала.

```bash
cat /home/rsolikhov/benchmarks/nsu-v1/collection/*/summary.json
cat /home/rsolikhov/benchmarks/nsu-v1/collection/smoke_report.json
```

Повторный `smoke` тоже использует готовые ответы из чекпоинта. Чтобы проверить
новое фактическое получение ответов, укажите для проверки другой каталог.

После успешной проверки запускайте полный проход с теми же настройками и
каталогом, сменив `smoke` на `collect`. Уже сохранённые два ответа будут пропущены.
Флаг `--parallel-models` запускает обе модели одновременно с независимыми
очередями и лимитами; результаты разделены по каталогам моделей.
Для более длинной предварительной проверки используйте `collect --limit 3`.

```bash
benchmarking/run_tmux.sh --session meno-benchmark \
  --log-file /home/rsolikhov/logs/benchmark-collect.log \
  collect \
  --backend-env /home/rsolikhov/Meno-Deploy/.env.backend \
  --output-dir /home/rsolikhov/benchmarks/nsu-v1/collection \
  --models meno-lite gemma-4-12B-it \
  --model-revision meno-lite=0.1 \
  --model-revision gemma-4-12B-it=everest-current \
  --model-concurrency meno-lite=1 \
  --model-concurrency gemma-4-12B-it=8 \
  --parallel-models
```

Для запуска в текущей оболочке вместо помощника используйте
`uv run --project benchmarking --frozen python -u -m benchmarking collect` с теми же
аргументами. Если переменная `BENCH_API_TOKEN` уже задана в окружении, она имеет
приоритет над файлом `--backend-env`.

Каждый запрос проходит полный конвейер выбранной моделью — переписывание,
LLM-переранжирование, ответ. BGE-M3 и BGE-reranker остаются отдельными службами
поиска. По умолчанию ответ ограничен 4096 токенами, температура равна 0.
Обрезанный, пустой ответ или неполная трассировка считаются ошибкой записи.
Допускаются три попытки; после повторного запуска обрабатываются только
ошибочные и незавершённые записи.

Число 8 для Gemma обозначает восемь одновременно выполняемых диалогов RAG.
Внутренний реранкер может создавать несколько LLM-вызовов на диалог, поэтому
это число нельзя напрямую сравнивать с `--concurrency 64` сборщика графа.
Настройки меняются независимо через `--model-concurrency МОДЕЛЬ=ЧИСЛО`.
Пробный проход покажет нагрузку на локальные BGE-службы и CPU графового поиска.

Для одновременного сбора обеих моделей используйте один процесс с
`--parallel-models`. Он открывает общий журнал чекпоинтов и запускает отдельные
очереди Meno Lite и Gemma. При лимитах 1 и 8 суммарно выполняются до девяти полных
запросов RAG. GPU генераторов различаются, а графовый поиск, BGE-M3 и
BGE-reranker остаются общими ресурсами сервера meno.

Для перехода с последовательного режима в текущей tmux-сессии остановите
сборщик через `Ctrl+C`, дождитесь приглашения оболочки, обновите репозиторий
`git pull --ff-only` и повторите прежнюю команду с `--parallel-models`.
Завершённые ответы сохраняются, незавершённые запрашиваются повторно.
Этот флаг является настройкой исполнения и не изменяет отпечаток эксперимента.
Обновляется только сборщик; пересборка контейнера core не требуется.
Без флага модели по-прежнему обрабатываются последовательно.
Второй процесс в том же каталоге отвергается блокировкой, поэтому параллельные
очереди следует запускать одним процессом.

## Что сохраняется

Основной журнал чекпоинтов — `collection/checkpoints.sqlite3`. Сжатые записи
сохраняются отдельными транзакциями с WAL и `synchronous=FULL`. Файлы
`responses.jsonl.gz`, `errors.jsonl.gz` и `summary.json` в каталогах моделей
создаются из него после завершения или штатной остановки. После аварийного
завершения повторная команда восстановит выгрузки из SQLite. Копируйте весь
каталог после остановки процесса, включая возможные файлы `-wal` и `-shm`.

Каждая успешная запись содержит исходный вопрос и эталон, ответ, полный
HTTP-ответ API, точный запрос без секретов, длительность, отпечаток backend и
контрольную сумму записи. В `raw_response.pipeline_trace` находятся

- переписанные запросы, кандидаты graph local/naive и результаты слияния;
- оценки и отбор LLM-реранкера, исходные идентификаторы фрагментов и элементов;
- `final_context`, `qa_messages` и упорядоченный `final_evidence` с точными
  позициями в контексте, типами `document`/`entity`/`relation` и происхождением;
- `retrieved_contexts`, построенный только из реально переданных доказательств;
- фактические `finish_reason`, `usage`, параметры и ответ генератора.

Трассировка содержит сырые кандидаты, поэтому каталог результатов может быть
значительно больше файла вопросов. Ключи API не сохраняются в результатах.
Промежуточные ответы и usage судьи хранятся на втором проходе.

Изменение данных, промптов, кода backend, настроек поиска, модели или её версии
требует нового каталога эксперимента. При несовпадении сборщик останавливается,
сохранив прежние результаты. Параллелизм, тайм-аут, число попыток, журнал и
`--limit` можно менять. `--model-revision` фиксирует вашу метку версии весов;
API не может определить скрытую замену весов под тем же именем. При смене весов
меняйте эту метку и каталог. Проверка отпечатка выполняется до каждого запроса.

## Второй проход — судья и RAGAS

После замены Gemma на судью потребуются сохранённые результаты, HTTP API судьи
и BGE-M3. Backend, Qdrant, Meno Lite и прежняя Gemma для оценки не нужны.
Для текущего сбора из 1907 успешных ответов используйте `--allow-partial`.
Если один ответ Meno отсутствует, отчёт покажет 953 доступных ответа из 954,
а для Gemma — 954 из 954. Отсутствующий ответ не получает оценок и не считается
ошибкой судьи. Во время оценки каталог исходного сбора сохраняйте неизменным,
поскольку его контрольная сумма входит в идентификатор эксперимента.

Судья `qwen3.8-27b` работает на прежнем Everest endpoint. Для H100 можно
перевести веса в FP8 через `--quantization fp8` и увеличить окно, если это
поддерживает конфигурация модели. В текущем запуске заданы `--max-model-len 32768`,
`--max-num-seqs 25` и `--gpu-memory-utilization 0.8`. Квантование меняет численные результаты судьи; задайте
отдельную версию `qwen3.8-27b-fp8-v1` и сохраняйте её на протяжении оценки.
Резерв ответа RAGAS остаётся 4096 токенов. Проверка самых длинных контекстов
покажет, достаточно ли увеличенного окна.

Следующие команды предназначены для судьи, уже запущенного в FP8 с окном 32768.
Для прежнего FP16-сервиса укажите окно 15000 и отдельные имя версии и каталог.
Под root обновите только репозиторий сборщика. Вначале выполните `sudo -i`
отдельной командой и дождитесь приглашения root.

```bash
export PATH="/root/.local/bin:$PATH"
cd /home/rsolikhov/meno_ragu_stand
git pull --ff-only

benchmarking/run_tmux.sh --session meno-ragas-smoke \
  --log-file /home/rsolikhov/logs/benchmark-ragas.log \
  evaluate \
  --collection-dir /home/rsolikhov/benchmarks/nsu-v1/collection \
  --output-dir /home/rsolikhov/benchmarks/nsu-v1/judge-qwen38-27b-fp8-v1 \
  --judge-url http://everest.nsu.ru:9022/v1 \
  --judge-model qwen3.8-27b \
  --judge-revision qwen3.8-27b-fp8-v1 \
  --judge-context-tokens 32768 \
  --embedder-url http://127.0.0.1:8001/v1 \
  --embedder-model BAAI/bge-m3 \
  --max-tokens 4096 \
  --concurrency 4 \
  --allow-partial \
  --sample-order longest-context-first \
  --limit 1 \
  --attempts 1
```

Подключение к сессии root — `tmux attach -t meno-ragas-smoke`. Для отсоединения
нажмите `Ctrl+B`, затем `D`. Проверка считает пять метрик для одного ответа
каждой модели — 10 оценок. `--limit` применяется отдельно к каждой модели,
в том числе при пропусках в наборе. Порядок `longest-context-first` выбирает
ответы с наибольшей суммарной длиной блоков доказательств в символах.
Фактическое число токенов проверяется отдельно перед каждым вызовом судьи.

Если появляется `judge_context_length_exceeded`, увеличьте окно сервиса судьи
до размера, поддерживаемого моделью и доступной памятью. Нужный размер указан
в ошибке. Доказательства не обрезаются. После успешной проверки запустите полный
проход с тем же каталогом; готовые оценки будут пропущены.

```bash
benchmarking/run_tmux.sh --session meno-ragas \
  --log-file /home/rsolikhov/logs/benchmark-ragas.log \
  evaluate \
  --collection-dir /home/rsolikhov/benchmarks/nsu-v1/collection \
  --output-dir /home/rsolikhov/benchmarks/nsu-v1/judge-qwen38-27b-fp8-v1 \
  --judge-url http://everest.nsu.ru:9022/v1 \
  --judge-model qwen3.8-27b \
  --judge-revision qwen3.8-27b-fp8-v1 \
  --judge-context-tokens 32768 \
  --embedder-url http://127.0.0.1:8001/v1 \
  --embedder-model BAAI/bge-m3 \
  --max-tokens 4096 \
  --concurrency 8 \
  --allow-partial
```

Проверка окна использует готовые сообщения после добавления Instructor JSON-схемы
и параметры chat template, резервирует `--max-tokens` и 32 служебных токена.
Применяется меньшее из указанного и объявленного `/tokenize` окна. Ошибка
токенизатора блокирует соответствующий вызов; приблизительный подсчёт и
автоматическая обрезка контекста не применяются. Результаты проверок сохраняются
в `details.budget_checks`, ответы судьи и usage — в `details.http_calls`.
Увеличение окна, изменение порядка, лимита вопросов или параллелизма сохраняет
готовые оценки. Параметры генерации, имя модели, версия весов, набор метрик и
исходные ответы должны остаться прежними. Ключи API задаются через
`JUDGE_API_KEY` и `EMBEDDER_API_KEY` в окружении.

Судья должен поддерживать JSON-ответы в OpenAI-совместимом API. По умолчанию
передаётся `chat_template_kwargs.enable_thinking=false`; `--enable-thinking`
убирает это указание для шаблона модели. Используются исходные prompts RAGAS
на английском, ответы и контексты сохраняются на русском без перевода.
Предел параллелизма относится к вычисляемым метрикам; одна метрика может
содержать несколько запросов судье. Этот предел независим от первого прохода.

| Метрика | Что оценивается |
| --- | --- |
| `faithfulness` | Подтверждаются ли утверждения ответа доступными генератору доказательствами |
| `factual_correctness` | Совпадение фактов ответа с эталоном, F1 |
| `answer_relevancy` | Соответствие ответа вопросу, с BGE-M3 для сравнения вопросов |
| `context_precision` | Полезность и порядок переданных доказательств относительно эталона |
| `context_recall` | Покрытие фактов эталона переданными доказательствами |

Для графового RAG доказательствами считаются и документы, и текстовые описания
отобранных сущностей/связей. Список сохраняет порядок блоков финального промпта,
поэтому `context_precision` описывает этот смешанный порядок, а не только
ранжирование документов. Faithfulness проверяет ответ относительно контекста,
включая сводные описания графа. Она сама по себе не проверяет правильность
исходных рёбер графа. Эталонных документов в наборе нет; отдельная метрика
точности восстановления рёбер по этим данным не вычисляется.

Оценки сохраняются по одной метрике на вопрос и модель. Ошибка, NaN или Inf
дают `score: null` со статусом ошибки и не входят в среднее. Валидный ноль входит.
Отчёт `summary.json` показывает среднее, число успешных оценок и покрытие от
954 вопросов отдельно для каждой модели и метрики. Незавершённый первый проход
допускается только с явным `--allow-partial`, покрытие всё равно считается от
полного набора. Готовые метрики пропускаются при повторном запуске.

Дополнительно RAGAS кэширует успешные вызовы судьи и векторные представления.
Кэши разделены, ключ судьи учитывает endpoint, имя и версию модели, параметры,
версию адаптера и RAGAS. Смена судьи на прежнем Everest URL не смешивает оценки.
Автоматическая телеметрия RAGAS отключена. Полные артефакты и отчёты остаются
на сервере и не попадают в Git.

API метрик зафиксирован по [RAGAS v0.4.3](https://github.com/vibrantlabsai/ragas/tree/v0.4.3/src/ragas/metrics/collections).
Описание определений приведено в [документации RAGAS](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/).
