# Методология сравнения «Менон 1.1» и RAGU: что говорит литература и какой протокол нам нужен

Дата: 2026-11-15. Источники читались по полным HTML-версиям статей, кроме помеченных «(только аннотация)». Числа из чужих таблиц приведены как в источнике; наши собственные оценки помечены «наша оценка».

## 1. Статья и библиотека RAGU

**Статья существует.** Репозиторий стенда ссылается на `https://github.com/RaguTeam/RAGU` (пакет `graph_ragu`, зафиксирован на коммите `abd3f29` в `/home/devuser/Meno-RAGU-Core/pyproject.toml`). На странице библиотеки дан BibTeX статьи **«RAGU: A Multi-Step GraphRAG Engine with a Compact Domain-Adapted LLM»** (Komarov, Bondarenko, Shtuka, Sedukhin, Shuvalov, Dementyeva, Solovyov, Nikitin; arXiv 2607.11683, 13.07.2026); репозиторий помечен «[EMNLP 2026]», на arXiv площадка не указана ([GitHub](https://github.com/RaguTeam/RAGU), [arXiv](https://arxiv.org/abs/2607.11683)). Библиотека частично основана на nano-graphrag, то есть идейно наследует Microsoft GraphRAG ([GitHub](https://github.com/RaguTeam/RAGU)). Вторая статья той же команды — про SemEval-2026 Task 8 (ансамбль LLM для многоходового RAG), к графу отношения не имеет ([HF Papers](https://huggingface.co/papers/2605.04523)).

**Построение графа** (шесть этапов, [arXiv HTML](https://arxiv.org/html/2607.11683)):
1. Чанкинг (простой, семантический, «умный» с кросс-энкодером).
2. Двухэтапное извлечение: сначала сущности с проверкой по схеме NEREL (29 типов сущностей, 49 типов связей), затем связи только между проверенными сущностями.
3. Консолидация: группировка по (имя, тип), для частых сущностей — кластеризация DBSCAN и LLM-суммаризация описаний; то же для связей.
4. Иерархическая кластеризация Leiden.
5. LLM-отчёты по сообществам (заголовок, резюме, выводы).
6. Необязательная чистка (например, удаление изолированных вершин).

**Режимы поиска** ([arXiv HTML](https://arxiv.org/html/2607.11683), [GitHub](https://github.com/RaguTeam/RAGU)): LocalSearch (векторный поиск сущностей → связи, резюме сообществ, исходные чанки), GlobalSearch (ответ по резюме сообществ), NaiveSearch (обычный векторный RAG), MixSearch (несколько движков параллельно), QueryPlanEngine (разбиение вопроса на DAG подзапросов). Статья описывает движки одной строкой и **не оценивает их по отдельности**.

**Что использует наш стенд.** По `README.md` стенда — только `local` и `naive` по одному переписанному запросу, затем переранжирование (`src/meno_rag/stand/ragu_pipeline.py`: кросс-энкодер bge-reranker либо LLM-реранк, отдельные пороги для чанков и элементов графа). GlobalSearch и QueryPlanEngine стендом не вызываются. Следствие: «глобальные» вопросы стенд может выиграть только за счёт описаний сущностей/связей и резюме сообществ, попавших в local-выдачу, а не за счёт map-reduce по сообществам. Есть ли резюме сообществ в развёрнутом графе, нужно проверить отдельно: в коде сборки есть пути с `make_community_summary=False`.

**Оценка в статье** ([arXiv HTML](https://arxiv.org/html/2607.11683)): GraphRAG-Bench (Medical; 4 уровня), BioASQ, MuSiQue, 2WikiMultiHopQA; метрики — Answer Correctness (LLM-судья gemini-3-flash-preview), ROUGE-L, Coverage, Faithfulness, Evidence Recall; ответы генерирует gpt-4o-mini. Всё на английском; русскоязычной оценки QA нет.

| GraphRAG-Bench Medical, AC×100 (индекс Meno-Lite) | Факты | Сложное рассуждение | Суммаризация (AC / Cov) | Творческая генерация (AC / Cov / Faith) |
|---|---|---|---|---|
| LightRAG | 26.2 | 20.2 | 22.6 / 51.2 | 14.4 / 3.9 / 27.6 |
| HippoRAG 2 | 72.4 | 68.4 | 65.0 / 51.7 | 56.9 / 34.7 / 26.6 |

- **Где выигрывает:** полнота (Coverage) на суммаризации и творческих задачах (71.1 против 51.7; 57.4 против 34.7), Evidence Recall 84% против ≤76% у конкурентов.
- **Где проигрывает:** фактоиды (−18 п.) и сложное рассуждение (−15 п.) относительно HippoRAG 2. Обычный векторный RAG в этой таблице **не измерен**.
- **Многошаговые QA против NaiveRAG** (краткие промпты, AC): BioASQ 72.9 против 71.7; MuSiQue 40.1 против 36.6; 2Wiki 58.0 против 53.7 — выигрыш графа над собственным naive-режимом 1–4 п. При подробных промптах: 56.0/55.3, 43.5/41.7, 46.6/43.5. HippoRAG 2 на MuSiQue остаётся впереди (54.4).
- **Важное для нас наблюдение авторов:** разрыв с HippoRAG 2 на 2Wiki сжимается с 19.3 до 5.5 п. при смене формата ответа с подробного на краткий, то есть метрика AC против кратких эталонов **сильно зависит от многословности ответа**, а не только от поиска.
- **Ограничения, названные авторами:** качество графа зависит от извлекающей LLM; NetworkX не масштабируется на миллионы вершин; бенчмарк извлечения может пересекаться с обучающим распределением Meno-Lite; задержка запросов не измерялась. Стоимость индексации ≈8k токенов на документ (MS GraphRAG ≈40k).

## 2. Где графовый RAG выигрывает и где проигрывает: числа

**Microsoft GraphRAG** (Edge et al., [arXiv 2404.16130](https://arxiv.org/html/2404.16130)). Два корпуса по ~1–1.7 млн токенов, по 125 вопросов, **сгенерированных LLM по описанию корпуса** (персоны × задачи), эталонов нет. Попарный LLM-судья: глобальные режимы выигрывают у векторного RAG по comprehensiveness в 72–83% и по diversity в 62–82% сравнений; по directness векторный RAG лучше во всех сравнениях. По числу утверждений: ~31–34 на ответ у графа против 25–26 у векторного RAG. Авторы сами отмечают: всего два корпуса, доля выдумок не сравнивалась.

**LightRAG** ([arXiv 2410.05779](https://arxiv.org/html/2410.05779)). Тот же протокол (125 сгенерированных вопросов на корпус, судья GPT-4o-mini): победы над NaiveRAG в 60–85% (Overall: 67.6 / 61.2 / 84.8 / 60.0% на четырёх корпусах), над MS GraphRAG — около паритета по Overall (49.6–54.8%).

**Критика этого протокола** (Zeng et al., [arXiv 2506.06331](https://arxiv.org/html/2506.06331v1)): LightRAG против самого себя даёт 90% : 10% в зависимости от порядка ответов; разница в длине на 25 токенов (при средней ~200) сдвигает долю побед более чем на 50 п.; повторные прогоны дают разных победителей. После выравнивания длины, обмена позиций и повторов: LightRAG против NaiveRAG 39.06% вместо заявленных 66.70% — **знак результата меняется**; доля ничьих больше 20%.

**HippoRAG 2** ([arXiv 2502.14802](https://arxiv.org/html/2502.14802); первая версия — [arXiv 2405.14831](https://arxiv.org/abs/2405.14831)). F1, читатель Llama-3.3-70B:

|---|---|---|---|---|---|---|
| NV-Embed-v2 (плотный поиск) | 61.9 | 55.7 | 45.7 | 61.5 | 75.3 | 57.0 |
| MS GraphRAG | 46.9 | 48.1 | 38.5 | 58.6 | 68.6 | 49.6 |
| LightRAG | 16.6 | 2.4 | 1.6 | 11.6 | 2.4 | 6.6 |
| HippoRAG | 55.3 | 55.9 | 35.1 | 71.8 | 63.5 | 53.1 |
| HippoRAG 2 | 63.3 | 56.2 | 48.6 | 71.0 | 75.5 | 59.8 |

Recall@5: HippoRAG 2 против плотного поиска — MuSiQue 74.7/69.7, 2Wiki 90.4/76.5, HotpotQA 96.3/94.5, NQ 78.0/75.4. Вывод: графы с LLM-суммаризацией (GraphRAG, LightRAG, RAPTOR) **проигрывают сильному плотному поиску и на простых, и на многошаговых фактоидах**; выигрывает только граф, который возвращает исходные пассажи (PPR по графу), и заметно — лишь на 2Wiki (+9.5 F1).

На художественном корпусе граф даёт +8…+13 п. на рассуждении и суммаризации; на структурированном медицинском корпусе выигрыш лучших графов 1–3 п., а MS GraphRAG проигрывает 12–26 п. Релевантность контекста у графов низкая (MS GraphRAG на Medical 3–6% против 60–91% у RAG), промпт длиннее: 954 токена у RAG, ~40 тыс. у MS GraphRAG local, ~100 тыс. у LightRAG.

**RAG vs. GraphRAG** (Han et al., [arXiv 2502.11371](https://arxiv.org/html/2502.11371)), Llama-3.1-8B. NQ F1: RAG 64.78, Community-local 63.01, global 54.48. HotpotQA F1: 60.04 / 61.66 / 45.16; HippoRAG 2 63.01. MultiHop-RAG, точность:

| Метод | Inference | Comparison | Null | Temporal | Всего |
|---|---|---|---|---|---|
| RAG | 92.16 | 57.59 | 96.01 | 30.70 | 67.02 |
| Community-GraphRAG local | 86.89 | 60.63 | 80.07 | 50.60 | 69.01 |
| Community-GraphRAG global | 89.34 | 64.02 | 19.27 | 53.34 | 64.40 |
| HippoRAG 2 | 91.54 | 58.41 | 85.71 | 49.91 | 70.27 |

Ключевые выводы: (а) 13.6% вопросов решает только граф, 11.6% — только RAG, то есть системы **дополняют друг друга**; объединение контекстов даёт +6.4% к лучшему; (б) в граф попадает лишь ~65.5–65.8% сущностей-ответов; (в) на суммаризации по человеческим эталонам (ROUGE-2) RAG не хуже графа, global заметно хуже; (г) позиционное смещение судьи: GraphRAG-local выигрывает 97% сравнений, стоя первым, и 12% — стоя вторым. Сам MultiHop-RAG: 2556 вопросов (comparison 856, inference 816, temporal 583, null 301), лучший поиск Hits@10 = 0.7467, GPT-4 0.56 с найденным контекстом против 0.89 с эталонным ([arXiv 2401.15391](https://arxiv.org/html/2401.15391)).

**2026:** «Do We Still Need GraphRAG?» — агентный многораундовый поиск существенно сокращает разрыв плотного RAG с графом, преимущество графа остаётся на сложном многошаговом рассуждении ([arXiv 2604.09666](https://arxiv.org/abs/2604.09666), только аннотация, чисел не видел).

Общий вывод литературы: устойчивого превосходства графа нет; он полезен там, где ответ требует **соединить несколько документов через сущности**, и вреден там, где нужна точная деталь из одного места. Наши данные (паритет в среднем, плюс на «complex», минус на датах и диалоге) укладываются в эту картину.

### Где граф должен проигрывать

**L1. Одношаговый точный факт.**
- Какой адрес у приёмной комиссии НГУ?
- Как зовут декана экономического факультета?
- В каком году основан НГУ?
- По какому телефону обращаться в отдел аспирантуры?

**L2. Числа, таблицы, пороги.**
- Сколько бюджетных мест на направлении «Физика» в бакалавриате?
- Какой минимальный балл ЕГЭ по математике для поступления на ММФ?
- Сколько стоит год обучения на программе «Юриспруденция»?
- Каков размер государственной социальной стипендии?

**L3. Актуальность и даты.**
- До какого числа принимают документы в магистратуру в этом году?
- Когда ближайший день открытых дверей?
- Какое расписание работы библиотеки на каникулах?
- Когда начинается летняя сессия у первого курса?

**L4. Процедуры по одному документу.**
- Как оформить академический отпуск?
- Какие документы нужны для заселения в общежитие?
- Как восстановить утерянный студенческий билет?

**L5. Диалог и мета-вопросы.**
- «А на втором курсе?» (после вопроса о стипендии первокурсника).
- «А там есть общежитие?» (после вопроса о факультете).
- Кто ты и откуда берёшь информацию?

**L6. Вопросы без ответа в базе (проверка отказа).**
- Какой проходной балл на программу, которой в НГУ нет?
- Кто заведует кафедрой астрофизики на ГИ? (ложная посылка)
- Сколько студентов НГУ живёт в общежитии № 25? (несуществующий объект)

## 4. Методы оценки помимо RAGAS

**Почему RAGAS может вводить нас в заблуждение.**
- *Faithfulness* = доля утверждений ответа, выводимых из контекста ([RAGAS](https://arxiv.org/html/2309.15217)). Метрика не знает, верны ли утверждения и отвечают ли они на вопрос. Она растёт, когда ответ пересказывает контекст дословно, и когда контекст огромен и содержит всё подряд. RAGU подаёт в промпт описания сущностей и связей, уже написанные LLM, — пересказ такого текста «верен контексту» по построению, даже если описание в графе ошибочно. Поэтому +0.12 по faithfulness не доказывает меньшую долю выдумок. Проверено авторами только на 50 страницах Википедии с вопросами от ChatGPT.
- *Answer correctness* — взвешенная сумма F1 по утверждениям и эмбеддинговой близости; F1 = TP / (TP + 0.5·(FP + FN)), где FP — утверждения ответа, которых нет в эталоне ([документация RAGAS](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/answer_correctness/)). **Любая верная дополнительная деталь считается ошибкой.** Наши эталоны краткие, а ответы gemma — медиана 662–695 символов и списки в ~80% ответов (`/home/devuser/Meno-RAGU-Core/docs/ragas-2026-11/README.md`), поэтому метрика систематически штрафует полноту. Тот же эффект в статье RAGU: смена формата ответа меняет AC на 2Wiki на 12–17 п. ([RAGU](https://arxiv.org/html/2607.11683)).
- В мета-оценке RAGChecker корреляция RAGAS answer similarity с человеческим предпочтением — 48.31 (Pearson) против 61.93 у пофактовой оценки и 70.09 между людьми ([RAGChecker](https://arxiv.org/html/2408.08067)). ARES показывает точность RAGAS по релевантности контекста 31.4–35.9% ([ARES](https://arxiv.org/html/2311.09476)).

| Метод | Суть | Сильные стороны | Слабые стороны |
|---|---|---|---|
| **RAGChecker** ([arXiv](https://arxiv.org/html/2408.08067)) | Утверждения ответа и эталона; precision/recall; claim recall поиска; context utilization; noise sensitivity; hallucination; self-knowledge | Разделяет ошибки поиска и генерации; лучшая корреляция с людьми (61.93) | Английский; «нейтрально» и «противоречит» слиты; зависит от качества извлечения утверждений |
| **ARES** ([arXiv](https://arxiv.org/html/2311.09476)) | Дообученные лёгкие судьи + поправка prediction-powered inference по ≥150 человеческим меткам | Честные доверительные интервалы с учётом ошибок судьи | Требует обучения судей; межъязыковой перенос провален (τ = 0.33); нам полезна только идея PPI |
| **TREC 2024 RAG, AutoNuggetizer** ([arXiv 2411.09607](https://arxiv.org/html/2411.09607), [arXiv 2504.15068](https://arxiv.org/html/2504.15068)) | Наггеты vital/okay (до 20 на вопрос), разметка support / partial / not; главная метрика — строгая полнота по vital | На уровне систем τ = 0.887 с ручной оценкой; не штрафует лишние детали | На уровне одного вопроса τ лишь 0.36–0.54; LLM строже людей (support 27.2% против 35.6%); не ловит выдумки; полнота коррелирует с длиной |
| **FActScore** ([arXiv](https://arxiv.org/abs/2305.14251)) | Доля атомарных фактов ответа, подтверждённых источником | Точность на уровне фактов; автоматическая оценка с ошибкой <2% | Только precision, не полнота; проверен на биографиях |
| **Попарный LLM-судья** ([MT-Bench](https://arxiv.org/abs/2306.05685), [Wang et al.](https://arxiv.org/abs/2305.17926)) | Какой из двух ответов лучше | Чувствителен к малым различиям; GPT-4 согласуется с людьми >80% | Смещения по позиции, длине, собственному стилю; порядком ответов можно «перевернуть» 66 из 80 сравнений; без обмена позиций и ничьих непригоден |
| **Критерии GraphRAG** ([Edge et al.](https://arxiv.org/html/2404.16130)) | Comprehensiveness, diversity, empowerment, directness | Единственный способ оценить вопросы без эталона | Вопросы сгенерированы LLM; сильная зависимость от длины и позиции ([Zeng et al.](https://arxiv.org/html/2506.06331v1)); по человеческим эталонам вывод обратный ([Han et al.](https://arxiv.org/html/2502.11371)) |
| **Метрики поиска** | Доля вопросов, где эталонный документ попал в контекст; доля наггетов эталона, присутствующих в контексте | Не зависит от генератора и судьи | Нужна разметка эталонных документов; у графа «документом» может быть описание сущности |

**Надёжность судьи.** Известные смещения: позиция, многословность, предпочтение собственных текстов ([MT-Bench](https://arxiv.org/abs/2306.05685), только аннотация; [Panickssery et al.](https://arxiv.org/abs/2404.13076), только аннотация). У нас оба ответа пишет gemma, а судит Claude, поэтому самопредпочтение не различает системы; но судьи одного семейства ошибаются согласованно, и это лечится только человеческой проверкой подвыборки. ARES называет минимум 150 человеческих меток для калибровки ([ARES](https://arxiv.org/html/2311.09476)).

**Статистика** ([Miller, arXiv 2411.00640](https://arxiv.org/html/2411.00640)). Сравнивать только парно, по разностям на одних и тех же вопросах: SE = √(Var(d)/n). Вопросы одного диалога или одного исходного документа — кластер, иначе интервалы занижены до 3 раз. Размер выборки: n = (z_{α/2} + z_β)²·σ_d² / δ² ≈ 7.85·σ_d²/δ² при α = 0.05 и мощности 80%. Типовые эксперименты в NLP недостаточно мощны ([Card et al.](https://arxiv.org/abs/2010.06595), только аннотация).

Наша оценка σ_d: в прогоне RAGAS разность answer correctness RAGU v3 и Менона имеет интервал [+0.0057; +0.0346] при n = 941, откуда σ_d ≈ 0.23; из интервала в постановке задачи ([−0.022; +0.009], n ≈ 608) σ_d ≈ 0.20.

| σ_d парной разности | δ = 0.03 | δ = 0.05 | δ = 0.10 |
|---|---|---|---|
| 0.20 (RAGAS-подобная метрика) | 349 | 126 | 31 |
| 0.23 | 461 | 166 | 42 |
| 0.30 (ожидание для полноты по наггетам; измерить на пилоте) | 785 | 283 | 71 |
| 0.35 | 1068 | 385 | 96 |

Для попарного предпочтения (исход +1 / 0 / −1, σ ≈ 0.9 при 20% ничьих): чистый перевес 0.10 (55:45 без ничьих) требует ~640 вопросов, перевес 0.20 — ~160. Следствие: на ~600 вопросах мы различаем δ ≈ 0.03 в целом, но по одному типу вопросов из 100–150 штук — только δ ≈ 0.05–0.08.

## 5. Рекомендуемый протокол

### 5.1. Данные
- **Набор A:** ~600 вопросов с человеческими эталонами (стратифицированы по имеющимся категориям).
- **Набор B:** новые «графовые» вопросы типов G1–G7 из раздела 3, эталон собран из корпуса и проверен, с перечнем эталонных документов (URL) и для G2/G7 — с полным списком элементов. Чтобы набор не был подыгрыванием графу, писать вопросы **по документам корпуса, а не по графу RAGU** (иначе повторяется ошибка «вопросы из собственного индекса», [Zeng et al.](https://arxiv.org/html/2506.06331v1)); добавить контрольные L1–L3 из тех же документов.
- **Набор C:** 60–80 вопросов без ответа в базе и с ложной посылкой (L6) — у графа это слабое место ([Han et al.](https://arxiv.org/html/2502.11371)).
- Минимум на тип: **100 вопросов** (различаем δ ≈ 0.08–0.10), желательно 150; тип с меньше чем 50 вопросами в отчёте помечается как «описательно, без вывода». Суммарно набор B — 700–1000 вопросов.

### 5.2. Метрики

| № | Метрика | Определение | Роль |
|---|---|---|---|
| M1 | Полнота по vital-наггетам (строгая) | Доля vital-наггетов эталона с меткой support | **Главная** |
| M2 | Полнота по всем наггетам | support = 1, partial = 0.5 | Вторичная |
| M3 | Доля противоречий эталону | Утверждения ответа, противоречащие эталону / все утверждения | Главная по вреду |
| M4 | Доля неподтверждённых утверждений | Утверждения, которых нет ни в эталоне, ни в найденном контексте / все | Замена faithfulness |
| M5 | Корректность отказа | Набор C: доля честных отказов; наборы A/B: доля ложных отказов | Главная на C |
| M6 | Попарное предпочтение | Чистый перевес с обменом позиций, по критериям: правильность, полнота, полезность | Перекрёстная проверка M1–M3 |
| M7 | Полнота поиска | Эталонный документ в контексте; доля vital-наггетов, присутствующих в контексте | Диагностика |
| M8 | Использование контекста | Наггеты, которые есть и в контексте, и в ответе / наггеты в контексте | Диагностика генерации |
| M9 | Точность/полнота списка | Для G2/G7: по элементам эталонного списка | Главная на агрегации |
| M10 | Длина ответа, задержка, число токенов контекста | Как есть | Обязательный контекст к M1 и M6 |

Верные дополнительные детали (утверждение есть в контексте, но не в эталоне) **не штрафуются** — этим протокол отличается от RAGAS answer correctness. Утверждение, поддержанное только описанием сущности/связи из графа, считается отдельно («поддержано производным текстом»), и на подвыборке проверяется по исходному чанку.

### 5.3. Что видит судья и что возвращает

Судья никогда не видит названия систем; порядок ответов и идентификаторы рандомизированы; оформление источников приведено к единому виду.

**Шаг 1. Наггеты эталона** (один раз на вопрос; вход: вопрос, эталон).
```json
{"question_id": "...", "nuggets": [{"id": "n1", "text": "…", "importance": "vital|okay"}],
 "answerable": true, "reference_problem": null}
```
Не более 10 наггетов; для списочных вопросов — один наггет на элемент. Второй судья проверяет набор; расхождения по vital/okay решает третий. Наггеты наборов B и C просматривает человек выборочно (20%).

**Шаг 2. Разметка наггетов** (вход: вопрос, наггеты, один ответ).
```json
{"assignments": [{"id": "n1", "label": "support|partial|not_support|contradicts", "quote": "…"}],
 "response_type": "answer|partial_answer|refusal|clarification"}
```
**Шаг 3. Утверждения ответа** (вход: вопрос, эталон, ответ, найденный контекст с идентификаторами блоков).
```json
{"claims": [{"text": "…", "vs_reference": "matches|contradicts|not_in_reference",
             "vs_context": "supported|unsupported|contradicted", "context_ids": ["c3"],
             "relevant_to_question": true}]}
```
**Шаг 4. Контекст** (вход: наггеты, контекст): `{"nugget_in_context": {"n1": true, …}}`.

**Шаг 5. Попарное сравнение** (вход: вопрос, эталон, ответ 1, ответ 2; без контекста).
```json
{"correctness": "1|2|tie", "completeness": "1|2|tie", "usefulness": "1|2|tie",
 "overall": "1|2|tie", "reason": "…"}
```
Для глобальных вопросов (G4) добавляются comprehensiveness и diversity, а в промпте прямо сказано не предпочитать более длинный ответ; итог по G4 всегда показывается рядом с M1/M9 и длиной.

### 5.4. Сколько судей и как сводить
- Шаги 2–4: **два независимых судьи** (разные модели Claude) на каждый ответ; при расхождении метки — третий, итог по большинству. В отчёте — согласие (κ Коэна или α Криппендорфа) по каждой метке; «partial» — ожидаемый источник расхождений ([arXiv 2504.15068](https://arxiv.org/html/2504.15068)).
- Шаг 5: два судьи × два порядка = 4 вызова на пару. Исход вопроса: победа, только если перевес сохраняется в обоих порядках у большинства судей; иначе ничья ([Zeng et al.](https://arxiv.org/html/2506.06331v1), [Wang et al.](https://arxiv.org/abs/2305.17926)).
- Независимое семейство: локальный qwen-судья на подвыборке 150–200 вопросов по шагу 2 — проверка, что вывод не является свойством судей Claude.
- Оценка считается на уровне вопроса, затем усредняется; судьи не усредняются до сведения меток.

### 5.5. Как обнаруживать смещения судьи
1. **A против A:** один и тот же ответ на обеих позициях (100 пар) — доля ничьих должна быть близка к 100%; иначе промпт попарного судьи непригоден ([Zeng et al.](https://arxiv.org/html/2506.06331v1)).
2. **Позиция:** доля вердиктов, меняющихся при обмене порядка; при >15% попарная метрика остаётся только вспомогательной.
3. **Длина:** регрессия исхода на log отношения длин; показать перевес отдельно для пар с разницей длины <20%.
4. **Повтор:** 100 вопросов прогнать дважды — оценить шум судьи.
5. **Человеческая калибровка:** 150 вопросов, стратифицированных по типам и по исходу судьи; человек размечает наггеты и противоречия вслепую. Сообщить согласие судьи с человеком по каждой метке; если судья систематически строже или мягче, поправить средние по схеме PPI ([ARES](https://arxiv.org/html/2311.09476)).
6. **Подставные ответы:** 50 ответов с внесённой ошибкой в число или дату и 50 кратких верных ответов — судья должен ловить первое и не штрафовать второе.

### 5.6. Статистика и представление
- Главный анализ задаётся заранее: M1 и M3 на наборах A и B раздельно; всё остальное — вторичное.
- Парный бутстреп по вопросам (10 000 повторов), **кластерный** — по диалогу для многоходовых вопросов и по исходному документу для набора B ([Miller](https://arxiv.org/html/2411.00640)).
- По типам вопросов — поправка Холма; для бинарных исходов — тест Мак-Немара и счёт «лучше / равно / хуже».
- В каждой таблице: n, среднее каждой системы, разность, 95% интервал, число побед/ничьих/поражений, медианная длина ответа, медианная задержка.
- Вывод «система лучше на типе T» допустим, только если интервал разности M1 не включает ноль **и** M3 не хуже; «паритет» — только если интервал целиком внутри ±0.03.
- Обязательная таблица взаимодополняемости: доля вопросов, решённых только RAGU, только Меноном, обеими, ни одной ([Han et al.](https://arxiv.org/html/2502.11371) — 13.6% и 11.6%); она отвечает на практический вопрос, стоит ли маршрутизировать или объединять контексты вместо выбора одной системы.
- Формат: md + CSV + SVG в `docs/` репозитория; на графиках — разности с интервалами по типам вопросов, а не средние по системам.

### 5.7. Что этот протокол не решает
- Судьи одного семейства: остаточное общее смещение оценивается только человеческой подвыборкой.
- Набор B написан нами под гипотезу; результат на нём — «потолок пользы графа», а не оценка на реальном потоке вопросов. Долю графовых типов в реальных диалогах нужно измерить отдельно и взвесить итог.
- Свежесть: вопросы L3 зависят от даты сборки базы; эталон фиксируется на дату сборки, иначе обе системы штрафуются за устаревший корпус.
