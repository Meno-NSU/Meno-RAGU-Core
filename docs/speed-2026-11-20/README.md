# Ускорение RAGU с сохранением входов модели

По итогам раздельных измерений рекомендуются `EARLY_FIRST_QUERY=false`, `RERANK_PRIORITY=0`, `STREAM_SOURCE_ATTRIBUTION=false`, `GRAPH_HUB_MIN_EDGES=5000`, `RERANK_PROMPT_ORDER=legacy` и 16 фрагментов контекста. На сервере Gemma сохраняется `max_num_batched_tokens=32768`. Раннее выполнение и уменьшение размера пакета не дали устойчивого выигрыша при общей нагрузке; в отдельных режимах задержка выросла. Это выбор настроек скорости, а не заключение о готовности всего релиза: качество ответов, полнота данных и доступность проверяются отдельно.

`EARLY_RERANK` имеет значение только при включённом `EARLY_FIRST_QUERY`. При `EARLY_RERANK=false` с переписыванием перекрывается только поиск, оценивание моделью начинается на обычном этапе. Этот вариант тоже измерен и оставлен выключенным через `EARLY_FIRST_QUERY=false`. В последующих опытах использованы `RERANK_GUIDANCE=structured`, исправленный часовой пояс `Asia/Novosibirsk`, прежний источник вопроса `RERANK_QUESTION_SOURCE=resolved` и прежний порядок доказательств `QA_EVIDENCE_POLICY=legacy`. Изменения смыслового поведения не подменяют настройки исполнения.

Ресурс опыта — `stand-v6k3b`. Манифест источников, манифест фрагментов CAG и статистика локальной KB буквально совпали с опубликованной веткой HF `kb-v3.9`, закреплённой коммитом `4333c232`; совпали и все 106 записей частей с их контрольными суммами. Это проверка идентичности метаданных и заявленных контрольных сумм, без повторного чтения больших файлов частей. Сам стенд сохраняет отметку сборки `v3.9b-candidate`: совпадение метаданных KB и чисел документов не является независимой проверкой всех фактических байтов построенного стенда. [Контрольные суммы и границы проверки](corpus_provenance.json)

## Раздельные измерения при общей нагрузке

Все три опыта использовали восемь фиксированных самостоятельных вопросов, два уравновешенных временных блока и параллельность RAGU 1, 4 и 8. У повторов одного вопроса общий статистический вес: дополнительные повторы при параллельности 8 не считаются независимыми вопросами. Запросы к настоящему Менону подавались по расписанию через обычный API в режиме измерений без сохранения диалогов. Учитываются предложенные запросы, задержка их допуска и число запросов, действительно попавших под нагрузку RAGU. Эти короткие серии не устанавливают предельную пропускную способность или отсутствие потерь на всём пользовательском трафике.

| Опыт | Сравнение | Измеренных запросов RAGU / Менона | Ошибки RAGU / Менона |
|---|---|---:|---:|
| Два фактора | Ранний поиск с оцениванием 0/1 × priority 0/1 | 224 / 96 | 0 / 0 |
| Только ранний поиск | Ранний поиск 0/1, раннее оценивание выключено, priority 0 | 112 / 48 | 0 / 0 |
| Размер пакета Gemma | 32768 и 8192, четыре свежих запуска A–B–B–A | 112 / 48 | 1 / 0 |

Общие условия: один экземпляр графа на опыт, подготовленные окрестности хабов с порогом 5000, атрибуция после ответа, `legacy` и 16 фрагментов. Первый опыт выполнялся на версии `21c976c` с прежним протоколом ограничения выбора; второй — на `29939ce` с `structured` и исправленными часами; третий — на `bac6480`, дополнительно с кешем сокращений. Поэтому сравниваются плечи внутри каждого опыта; абсолютные времена разных опытов не объединяются. SHA исполненных драйверов и фактически импортированных исходников сохранены в числовых результатах.

В таблицах ниже разность положительна при замедлении включённого варианта. Оценка — средняя парная разность с равным весом восьми вопросов, после усреднения повторов каждого вопроса. Интервалы получены перевыборкой вопросов, а не отдельных ответов; это номинальные 95%-интервалы без поправки на множество сравнений. Внешняя нагрузка и временной порядок остаются ограничениями. Эффекты взаимодействуют, поэтому значения первых двух строк не следует складывать как независимые выигрыши. Трассы согласуются с конкуренцией раннего оценивания и переписывания на общей модели. Само по себе совпадение хешей контекста не доказывает одинаковое качество сгенерированных ответов. [Полные агрегаты двух факторов](load_factorial.json)

Для полного времени интервал пересекает ноль. При параллельности 4 среднее полное время контрольного Менона выросло на 1,247 с [0,169; 2,261], но в сравнении всего восемь пар контрольных запросов. ## Размер пакета и доступность модели

Для проверки 32768 против 8192 Gemma четырежды запускалась заново в порядке A–B–B–A. Во всех блоках одинаковы фактические файлы основной модели, вспомогательной модели и токенизатора, версия vLLM, параметры запуска кроме проверяемого лимита, стандартный запрос готовности и общий прогрев восьмью вопросами. Кеш не очищался отдельным вызовом: после запроса готовности он уже не буквально пуст. Отпечатки построены по содержимому файлов, а не только по имени модели. Возврат к 32768 также выполнен свежим запуском.

Уменьшение до 8192 увеличило ожидание первого токена RAGU при параллельности 4 на 1,768 с [0,169; 3,603], при параллельности 8 — на 0,847 с [0,163; 1,556]. При параллельности 8 подготовка выросла на 0,788 с [0,086; 1,474]. Полное время контрольного Менона при параллельности RAGU 4 выросло на 2,843 с [0,261; 6,443]. Интервалы полного времени самого RAGU пересекают ноль. Оснований переводить сервер на 8192 нет; сохраняется исходное 32768. [Полные агрегаты размера пакета](maxbatch.json)

Из 112 измеренных запросов RAGU завершились 111. Один запрос в первом блоке 8192 при параллельности 1 получил HTTP 503 от временного посредника до генерации ответа. Наблюдатель зафиксировал единственную ошибку его соединения с H100 в интервале, содержащем завершение этого запроса; зарегистрированных HTTP-ошибок самой модели не было. Точный подкласс транспортной ошибки не сохранён, поэтому её нельзя приписывать конкретному механизму или считать доказанным следствием лимита 8192. Тот же вопрос в остальных трёх блоках завершился с одинаковым контекстом. Неудачный запрос остаётся в знаменателе 112; сравнение задержек при параллельности 1 использует 15 успешных пар, а не 16.

Оба наблюдателя завершились: по 1332 выборки, ошибок чтения нет. Все измеренные фазы охвачены выборками до и после фазы без смены экземпляра. Во время этих фаз счётчики посредника не показывают обращений к резерву A6000, а прямой наблюдатель A6000 — завершённых генераций. Так подтверждён фактический H100 для измеренного окна; частота опроса сама по себе не исключала бы короткое переключение. Вне измеренных фаз посредник переключался на резерв при управляемых перезапусках. Это не проверка автоматического переключения при отказе сервера. ## Кеш поиска сокращений на CPU

Полный функциональный повтор позднее обнаружил два изменённых промпта из-за
раздельной токенизации частей. Исправленный кеш обрабатывает полную исходную
строку. Приведённые ниже времена относятся к прежней реализации; переносить
их на исправленную версию нельзя.

Кеш хранит неизменяемые множества слов и основ слов для полного текста документа и вопроса с историей; форматирование выполняется по актуальному словарю сокращений. Кеш ограничен ресурсами одного стенда, 2048 записями и 64 МиБ с учётом текста ключей, множеств, строк и накладных расходов записей; при загрузке корпуса он пуст. Полные промпты обоих порядков буквально совпали на всех 10 548 общих парах сохранённых вызовов: 21 096 проверок из 21 096.

На этих же данных измеряемый участок CPU сократился с 69,201 до 56,582 с. Для 100 разных сочетаний вопроса и истории это около 126 мс на запрос. Снижение на 18,2% относится только к проверяемому CPU-участку; такого ускорения полного ответа не измерено. [Отдельный отчёт о кеше](../abbreviation-cache-2026-11-20/README.md)

Далее сохранена история первоначального смешанного пилота и проверок отдельных механизмов. Она не заменяет раздельные измерения выше. В частности, прежние 96 совпадений из 100 — проверка ранней реализации на фиксированных ответах модели, а не полное доказательство эквивалентности окончательного кандидата всем 1454 заданиям.

Скрипты `aggregate_factorial.py`, `aggregate_retrieval_only.py` и `aggregate_maxbatch.py` пересчитывают соответствующие сводки по числовой выгрузке без HTTP-запросов и моделей. Запуск: `python <скрипт> <числовая_выгрузка.json> --output <сводка.json>`. Две проверки в `test_numeric_analysis.py` подтверждают равный вес вопросов при повторах и сохранение ошибки отдельного запроса в общем знаменателе. Исходные тексты вопросов, ответы, контексты и закрытые пути в эти публикации не входят. Контрольные суммы агрегатов, наблюдений и скриптов перечислены в [манифесте результатов](matrix_artifacts.json).

## Первоначальный пилот и проверки механизмов

20 ноября 2026, Новосибирск. Исходная версия `main` — `7773794`. Для проверки взяты незавершённые ветки `perf/early-first-query` и `perf/identical-speedups`, записи вызовов Gemma и стенд `stand-v6k3b`.

Кандидат объединяет ранний поиск, подготовленные окрестности хабов и подбор источников во время потока ответа. В нём исправлены три ошибки раннего исполнения и два нарушения контракта потоковой атрибуции. Изменения используют состояние задач, оценки и связи графа. Условий по темам, именам и тексту вопроса нет. Порядок промпта переранжирования остаётся `legacy`, размер контекста — 16 фрагментов.

В исходной реализации ранний запрос мог задержать запуск остальных. Ошибка или отмена в обработчике завершения стадии переписывания оставляла фоновые задачи вне cleanup. При пустом или одиночном первом пуле терялся прогрев префикса `question_first`. Все три случая воспроизведены тестами и исправлены. Режим раннего поиска включается через `EARLY_FIRST_QUERY=true`.

Для хабов используется `GRAPH_HUB_MIN_EDGES=5000`, по умолчанию 0. Порог выбирает узлы по числу связей. Кеш относится к загруженному статичному графу. При полном пуле кандидатов подготовленные сокращённые списки не применяются.

Потоковый подбор источников доступен через `STREAM_SOURCE_ATTRIBUTION=true`, по умолчанию выключен. Его изолированная польза под нагрузкой пока не измерена. При выключенной настройке используется прежний подбор после завершения текста. В живом пилоте ниже B использовал потоковый подбор; числа этого плеча относятся к этой конфигурации. Добавление выключателя после пилота сохраняет проверенную реализацию, но требует явного включения для воспроизведения B. SHA исполненного скрипта и версии кода сохранены в результате.
