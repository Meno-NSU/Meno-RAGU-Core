# Реестр «подразделение — персона — должность»: подготовка (не запускалось)

Предложение 3 аудита навигации (`~/meno-v2/audit1119/nav/REPORT.md` на проде). Здесь входы, промпт с обязательной
проверкой дословного фрагмента, схема рёбер со временем и оценка числа вызовов. Извлечение не запускалось.
Инструмент: `tools/registry_extract.py` (`plan` — только подсчёт входов, `run` — извлечение).

## Зачем

В графе v6 у рёбер нет времени, должностей почти нет: 4 463 ребра `HEAD_OF`, год в описании у 10%; у 526
подразделений по два и более «руководителей» без периода (у ММФ 18, включая «Марчук является деканом» и

## Промпт и проверка фрагмента

Системный промпт (`registry-v1`, в `registry_extract.py`): вернуть JSON-массив записей; у каждой `evidence` —
непрерывный фрагмент страницы, скопированный дословно, без пропусков и многоточий; все значения записи должны
стоять в этом фрагменте; чего нет — `null`; даты только те, что написаны на странице.

Проверка после ответа (`checked`), без модели:

1. `evidence` после сжатия пробелов и приведения регистра — подстрока страницы. Нет — запись отбрасывается.
2. Каждое значение записи — подстрока её `evidence`. Нет — поле отбрасывается (логические поля и `null` не
   проверяются).
3. В выход пишутся счётчики: записей принято, записей без дословного фрагмента, значений вне фрагмента.

В пробе 18.11 без этого требования дословный фрагмент был у 18 из 26 записей: модель ставила «…» между кусками.
Поэтому проверка обязательна, а доля отброшенных записей — первый показатель качества промпта.

## Рёбра со временем

Каждая принятая запись становится ребром (или узлом) с одинаковым набором служебных полей:

```yaml
edge:
  type: HOLDS_POSITION            # Appointment: PERSON -> ORG_UNIT
  subject_id: pure:person:<uuid> | sveden:employee:<якорь карточки>
  object_id:  pure:org:<uuid> | struktura:<путь от корня>
  attributes: {position, employment_condition, is_head_of_unit}
  valid_from: дата со страницы или null
  valid_to:   дата со страницы или null
  as_of:      дата версии страницы (kb_source_version_id -> дата обхода)
  first_seen: дата первого снимка, где запись есть
  last_seen:  дата последнего снимка, где запись есть
  source: {url, source_version, evidence}
  generator: {model, prompt_version}
```

- `PART_OF` (Unit → parent_unit), `TEACHES` (Teaching), `HAS_DEGREE` (Qualification) — те же служебные поля.
- `HEAD_OF` не хранится отдельно: это `HOLDS_POSITION` с `is_head_of_unit = true`.
- «Сейчас»: записи, у которых `valid_to` пуст и `last_seen` равен последнему снимку источника. Запись,
  пропавшая из нового снимка, закрывается: `valid_to` = дата этого снимка, пометка «закрыто по снимку».
  История не удаляется.
- Противоречие (два действующих руководителя одного подразделения из разных источников) не разрешается
  правилом: обе записи остаются, в контекст идут обе с датами `as_of`.
- Идентичность: подразделение и персона сводятся по идентификатору источника (UUID Pure), карточка
  `sveden/employees` привязывается к персоне Pure через блок «Данные исследовательского портала» той же
  карточки; сведение по одному имени не делается (у 1 247 из 2 168 карточек фамилию делят два и более узла).

## Оценка вызовов

- 6 182 вызова; вход ≈ 12,05 млн символов страниц + системный промпт ≈ 5–6 млн токенов; выход по пробе
  ≈ 0,4–0,8 тыс. токенов на карточку ≈ 3–5 млн токенов.
- В пробе 18.11 при занятом сервере (до 55 чужих запросов) карточка сотрудника занимала 14–49 с, карточка
  программы 6–15 с. При 16 одновременных запросах и 20 с на вызов — около 2 ч; при 2 запросах — около 17 ч.
  Запускать в окно, когда H100 не нужен продакшену, с тем же ограничителем, что у сборки графа
  (`llm_proxy.py`).
- Перед полным прогоном: 100 случайных страниц на источник, доля записей без дословного фрагмента и доля
  значений вне фрагмента; ручная сверка 50 записей `Appointment` со страницей.

## Что не входит

его надо брать с сайта построчно, без модели.
