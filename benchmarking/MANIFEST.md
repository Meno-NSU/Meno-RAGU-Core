## 2. Цель и единица сравнения

Цель — оценить ответы русскоязычного диалогового сервиса о НГУ, который использует
корпус документов и граф знаний RAGU. Сравниваются два варианта полного конвейера
с генеративными моделями Meno Lite 0.1 и Gemma.

В каждом варианте одна выбранная генеративная модель выполняет три задачи —
переписывание вопроса, LLM-переранжирование и формирование ответа. Общими остаются
корпус, граф, BGE-M3, BGE-reranker и программная реализация. Переписанные запросы,
отбор доказательств и объём доступного контекста могут различаться между
вариантами. Поэтому результат характеризует полный конвейер с выбранной LLM;
он не изолирует качество финального генератора на одинаковом контексте.

Единица первого прохода — один вопрос и один ответ модели без истории диалога.
Единица второго — одна метрика для одного сохранённого ответа одной модели.
Первый проход не обращается к судье. Второй не повторяет поиск и генерацию.

## 6. Путь поиска и формирования контекста

Для каждого вопроса выполняется следующая последовательность.

1. Локальная обработка аббревиатур и генеративное переписывание запроса.
2. Поиск по переписанным запросам в двух режимах RAGU — local по окружению графа
   и naive с плотным BGE-M3 и разреженным BM25-поиском.
3. Обработка кандидатов специализированным BGE-reranker и формирование смешанного
   пула фрагментов, сущностей и связей с оценками и происхождением.
4. Слияние повторяющихся кандидатов по типизированным идентификаторам,
   LLM-переранжирование выбранной генеративной моделью и отбор доказательств.
5. Сборка контекста с документами и текстовыми описаниями элементов графа,
   проверка окна выбранной LLM и генерация ответа.

Значения ниже — значения `Settings` зафиксированной версии кода. Фактические
переопределения сервера проверяются по отпечатку и трассировке сбора.

| --- | ---: |

| `GRAPH_TOP_K`, local-поиск | 20 |
| `ENGINE_RERANK_TOP_K` | 30 |
| `GRAPH_RELATED_CANDIDATES`, связи/фрагменты/сводки перед реранкером | 200 |
| `GRAPH_SOURCE_DOCUMENTS`, на элемент графа | 5 |
| `MAX_REWRITE_QUERIES`, включая исходный вопрос | 8 |
| `RERANK_CANDIDATES_PER_QUERY` | 40 |

В отдельном Docker backend few-shot дополнительно отключён конфигурацией

этот порядок не следует интерпретировать как глобальный список кандидатов
по убыванию исходной оценки поиска.

## 7. Первый проход — сбор ответов

Backend бенчмарка доступен на `http://127.0.0.1:9007`. Запрос отправляется в
`/v1/chat/completions` с `knowledge_base_id=nsu-ragu`, одним сообщением пользователя,
`stream=false`, запрошенными `temperature=0` и `max_tokens=4096`.

| Генеративный этап | Параметры реализации |
| --- | --- |
| Переписывание | temperature 0.1, max_tokens 1024, seed 42 |
| Основной LLM-реранкер | temperature 0, max_tokens 1, logprobs, top_logprobs 5, варианты 0/1/2 |
| Резервный JSON-реранкер | temperature 0, max_tokens 20 |
| Финальный ответ | Запрос бенчмарка temperature 0, max_tokens 4096; seed 42 в API-конвейере |

API применяет нижний предел `MIN_OUTPUT_TOKENS` к резерву финального ответа.
Поэтому значение 4096 здесь описывает запрос сборщика; источником эффективных
параметров служит `trace.generation.sampling`. Поле
`generation_sampling_defaults` содержит значения класса по умолчанию и не
заменяет применённые параметры конкретного ответа.

`enable_thinking=false` передаётся в LLM-переранжирование. При переписывании и
финальной генерации этот параметр явно не задаётся, действует шаблон сервера.
По данному протоколу нельзя утверждать, что reasoning у Gemma был отключён
на всех этапах первого прохода. В системное сообщение QA включается текущее
время; фиксированный seed не делает повторный запрос в другой момент побайтово
идентичным. В судейский проход передаются исходные сохранённые ответы.

`BENCH_API_TOKEN` включает режим без записи тестовых диалогов в таблицы API и
с обязательной полной трассировкой. Токен проверяется до первого запроса генерации;
`X-Benchmark-Fingerprint` защищает проход от смешивания конфигураций backend.
API-ключи из настроек и заголовки Authorization в манифест и результаты
не записываются.

Meno Lite обрабатывается с лимитом 1 полного запроса RAG, Gemma — 8.
Режим `--parallel-models` позволяет обеим очередям работать одновременно с общим
журналом. Первые записи могли быть получены последовательным запуском и затем
использованы из чекпоинта. Смена параллелизма не меняет состав эксперимента.
Генераторы находятся на разных GPU, но поиск, BGE-M3 и BGE-reranker у них общие.

Успешная запись требует непустого ответа, фактического `finish_reason=stop`,
трассировки версии 2, точных непустых доказательств и совпадения их позиций
с финальным контекстом. Обычно допускаются три попытки на запись.
HTTP-ошибки, обрезанный ответ или неполная трассировка не превращаются
в успешный ответ. Одновременное сохранение двух процессов в один каталог
запрещено файловой блокировкой.

| Модель | Запланировано | Сохранено | Отсутствует |
| --- | ---: | ---: | ---: |
| Meno Lite | 954 | 953 | 1 |
| Gemma | 954 | 954 | 0 |
| Всего | 1908 | 1907 | 1 |

У Meno отсутствует `index=785` при нумерации с нуля. Это установлено пересечением
индексов исходного набора и доступных ответов в полной судейской выгрузке;
причина сбоя сбора по этой выгрузке не восстанавливается. Эталон вместо
отсутствующего ответа не подставляется.

`/home/rsolikhov/benchmarks/nsu-v1/judge-qwen38-27b-fp8-v1`.

1907 ответов; для них запланировано 9535 оценок. Десять успешных оценок smoke

окончательная ошибка; из девяти ошибочных попыток по семи заданиям шесть
заданий впоследствии успешно завершились. Оставшаяся ошибка Gemma при
`index=205` относится к лимиту ответа судьи 4096, а не к отсутствию ответа
генератора или автоматически нулевому качеству ответа.

Перед каждым фактическим HTTP-вызовом судьи проверяется готовый запрос после
добавления JSON-схемы Instructor. В `/tokenize` передаются те же сообщения и
параметры chat template. Условие допуска

`prompt_tokens + reserved_output_tokens + 32 <= min(32768, served_max_model_len)`.

Ошибка подсчёта или превышение окна дают явную ошибку метрики. Контекст не
обрезается и не заменяется сводкой. Результат проверки хранится в
`details.budget_checks`. Проверка не требуется для результата, возвращённого
из кэша без HTTP-вызова. Увеличение окна при сохранении остальных параметров
не сбрасывает успешные оценки; смена весов или квантования требует новой
метки версии и нового каталога оценки.

## 9. Метрики RAGAS 0.4.3

Обозначения — `q` вопрос, `a` сохранённый ответ, `r` эталон, `C₁…Cₙ`
упорядоченные доказательства финального промпта. Используется современный API
`ragas.metrics.collections`, вызов `await metric.ascore(...)`, поле результата
`MetricResult.value`.

| Имя в отчёте | Класс | Входы |
| --- | --- | --- |
| `faithfulness` | `Faithfulness` | `q`, `a`, `C` |
| `factual_correctness` | `FactualCorrectness` | `a`, `r` |
| `answer_relevancy` | `AnswerRelevancy` | `q`, `a` |
| `context_precision` | `ContextPrecisionWithReference` | `q`, `r`, `C` |
| `context_recall` | `ContextRecall` | `q`, `r`, `C` |

### 9.1. Faithfulness — подтверждение ответа контекстом

Судья выделяет самостоятельные утверждения из ответа и проверяет их по
объединённым доказательствам. Результат — доля подтверждённых NLI-вердиктов
в возвращённом судьёй списке. Эталонный ответ не используется.
Знаменатель определяется реально возвращённым списком, его соответствие числу
изначально выделенных утверждений отдельно не проверяется. Пустой список
утверждений или проверок возвращает NaN.

Высокая faithfulness у обоснованного отказа возможна при нулевой способности
ответить на вопрос. Она не заменяет factual correctness или relevancy.

### 9.2. Factual correctness — соответствие эталону

Параметры — `mode=f1`, `atomicity=low`, `coverage=low`, `beta=1.0`.
Утверждения ответа проверяются по эталону, а утверждения эталона — по ответу.
В реализации RAGAS 0.4.3 `TP` — подтверждённые утверждения ответа, `FP` —
неподтверждённые утверждения ответа, `FN` — неподтверждённые утверждения эталона.
Вычисляются `P=TP/(TP+FP)`, `R=TP/(TP+FN)` и F1, результат округляется до
двух знаков. Нулевые знаменатели обрабатываются как нули; пустая декомпозиция
может дать валидный нулевой результат.

Значение определяется эталоном и декомпозицией судьи. Метрика не выполняет
независимую внешнюю проверку фактов и не получает найденные доказательства
или исходный вопрос. В полном проходе ручной аудит выявил ложные отрицания,
когда самодостаточный ответ называл событие из вопроса, а короткий эталон
его не повторял; примеры и оговорки приведены в итоговом отчёте. Это ограничение
интерпретации оценок, а не дополнительное правило исходного протокола.
Параметр `coverage=low` относится к детализации декомпозиции, а не к числу
оценённых вопросов в итоговом отчёте.

### 9.3. Answer relevancy — соответствие ответа вопросу

При `strictness=3` судья восстанавливает вопросы по ответу и выставляет флаг
`noncommittal`. BGE-M3 сравнивает исходный вопрос с восстановленными через
косинусное сходство. Результат — среднее сходство; если все полученные флаги
`noncommittal` истинны, результат равен нулю. При отсутствии
непустых восстановленных вопросов также возвращается ноль.

В RAGAS 0.4.3 три запроса используют одинаковые prompt и схему и идут
последовательно. В данном протоколе кэш и temperature 0 приводят к повторному
использованию первого результата. Фактически усредняются три копии одного
восстановленного вопроса; это не три независимых суждения. Такое поведение
подтверждено скачанными результатами smoke.

Векторы получаются HTTP-запросами BGE-M3 без перевода исходных строк и без
OpenAI-токенизации или параметра `dimensions`. Восстановленные судьёй вопросы
могут оказаться на английском. Высокое сходство не доказывает правильность
фактов. Косинус математически может быть отрицательным; используемый путь
`ascore` и адаптер не выполняют принудительное обрезание до диапазона `[0,1]`.

### 9.4. Context precision — полезность и порядок доказательств

Каждый блок `Cᵢ` оценивается по вопросу и эталону. Для бинарной полезности `uᵢ`
вычисляется `P@i=(Σⱼ≤ᵢ uⱼ)/i`, затем

`score = Σᵢ(P@i × uᵢ) / (Σᵢuᵢ + 10⁻¹⁰)`.

Это average precision полезности блоков финального промпта. Порядок отражает
сборку документов и элементов графа, а не только ранжирование сырых кандидатов
RAGU. При отсутствии полезных блоков ноль является штатным результатом.
Сохранённый ответ генератора в эту метрику не передаётся.

### 9.5. Context recall — покрытие эталона доказательствами

Судья классифицирует утверждения эталона по объединённым доказательствам.
Результат — `Σ attributed / число возвращённых classifications`.
Пустой список возвращает NaN. Ответ генератора не используется.
Это полнота покрытия фактов эталона, а не recall поиска по размеченному
перечню исходных документов — такой разметки в наборе нет.

### 9.6. Язык и пределы автоматической проверки

Вопросы и эталоны поступают в исходном виде. Используются стандартные английские
инструкции и примеры RAGAS; отдельная русскоязычная адаптация промптов не
выполнялась. Язык промежуточных утверждений не закреплён, в smoke встречался
английский перевод.

Бинарность verdict и attributed задаётся инструкцией, но типы в библиотеке —
`int`, без жёсткого перечисления 0/1. Полнота возвращённых списков утверждений
отдельно не контролируется. Адаптер проверяет, что итоговый результат — конечное
число; соответствие суждений содержанию дополнительно проверяется по аудиту.

## 10. Адаптация к графовому RAG

В `retrieved_contexts` включаются только блоки, действительно переданные
генератору после ограничений бюджета. Это тексты документов, описания сущностей
и связей графа. Их текст и порядок сохраняются; проверяются точные позиции
в финальном контексте. Сырые кандидаты, исключённые реранкером или бюджетом,
в RAGAS не подмешиваются.

Типы и идентификаторы, оценки кандидатов и происхождение элементов графа
сохраняются отдельно в трассировке первого прохода. Ссылки на исходные фрагменты
передаются через глобальные индексы Menon после отображения RAGU.

Метрики оценивают доступные генератору текстовые доказательства. Они напрямую
не измеряют правильность рёбер, качество выделения сущностей, точность
сообществ или полноту самого графа. Faithfulness относительно сводного описания
графа не удостоверяет его истинность относительно исходного документа.
Для таких выводов потребуются отдельная разметка и дополнительные метрики.

## 12. Чекпоинты, кэш и продолжение

SQLite работает с WAL и `synchronous=FULL`. Каждый успешный ответ и каждая
успешная метрика фиксируются собственной транзакцией; payload сжимается gzip.
История попыток хранит время и сведения об ошибках. JSON-выгрузки и сводки
создаются атомарной заменой после завершения или штатной остановки.
После аварии авторитетным остаётся SQLite; выгрузки восстанавливаются повторным
запуском. Для копирования SQLite используйте остановленный процесс и учитывайте
возможные `-wal`/`-shm` либо корректный SQLite backup.

Повторный запуск пропускает `complete` и обрабатывает ошибочные или незавершённые
задания. Внутренние успешные вызовы незавершённой метрики могут использоваться
из кэша RAGAS. Кэш судьи разделяется по URL, alias, версии, параметрам генерации
и версии адаптера; кэш векторов — по собственной конфигурации BGE. Batch
embeddings дополнительно обёрнуты кэшированием.

Параллелизм, тайм-аут, число попыток, порядок вопросов, `--limit` и предел окна
для проверки можно менять без сброса успешных оценок. Смена исходных ответов,
судьи, версии весов, квантования, параметров генерации или набора метрик требует
отдельного каталога. Метка версии должна отражать смену модели даже при том же
URL и alias. Во время судейского прохода исходную коллекцию не дополняют.

Расход токенов в `details.usage` учитывает наблюдавшиеся некэшированные HTTP-
вызовы и не является пересчётом всей вычислительной работы, включая попадания
в кэш и подготовку корпуса. Проверки `/tokenize` не расходуют токены генерации.
Телеметрия RAGAS отключается через `RAGAS_DO_NOT_TRACK=true`.

## 13. Агрегация и правила публикации результатов

Среднее считается отдельно для каждой модели и каждой метрики с одинаковым
весом каждого успешно оценённого вопроса. NaN, Inf и исключения дают
`score=null` со статусом ошибки и исключаются из среднего. Валидный ноль
включается в среднее. При отсутствии успешных оценок среднее равно null.

`coverage = scored / 954`. Поля `available_answers` и `missing_answers`
показывают полноту первого прохода отдельно от `failed_or_interrupted`
судейского этапа. Невыполненные ещё задания не следует считать ошибками.
Число обработанных записей в журнале включает успешные и исчерпавшие попытки;
успешность проверяется по `scored`, статусам SQLite и коду завершения.

Исходный runner формирует отдельные средние в `summary.json`; он не считает
единый балл по пяти метрикам, доверительные интервалы, статистические тесты
или автоматическое пересечение вопросов двух моделей. Средние 953 и 954
ответов в этой сводке не являются парным сравнением идентичной выборки.

После завершения прохода [analyze_results.py](analyze_results.py) отдельно
выполняет offline-анализ неизменённых оценок. Для каждой метрики выбирается
пересечение успешных `sample_id`: 953 пары для четырёх метрик и 952 для
`factual_correctness`, где дополнительно исключён `index=205` Gemma. Разность
определена как Gemma минус Meno. Применён парный percentile bootstrap:
10 000 повторов, seed 42 заново для каждой метрики, порядок исходных пар —
лексикографический по `sample_id`; границы 95% интервала — квантили 2.5% и
97.5% средних разностей при повторной выборке пар с возвращением.
Параметры и результаты находятся в [analysis.json](results/nsu-v1/analysis.json).

Эти интервалы отражают вариативность набора вопросов при фиксированных
сохранённых оценках. Они не учитывают ошибки судьи, смещения промптов,
неточности эталонов, случайность новой генерации или систематические ошибки
декомпозиции. В частности, интервал, исключающий ноль, не удостоверяет
преимущество в человеческой оценке фактической правильности. Bootstrap
не меняет исходные баллы и не добавляет новые вызовы моделей.

В публикацию следует включать версии моделей и протокола, coverage каждой
метрики, число отсутствующих ответов и ошибок судьи. Повторяющиеся меню сайта
и общие списки подразделений, обнаруженные в smoke, являются наблюдением
о качестве эффективного контекста; распространённость проблемы по двум
вопросам не оценивается.
