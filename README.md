# Meno-RAGU-Core: серверная версия стенда

`meno_ragu_stand` — новый core для существующего Meno-Web. HTTP API, авторизация,
гостевые сессии, история, арена, обратная связь, согласия и потоковые события SSE
совместимы с production-backend. Поиск выполняется только через RAGU: local + naive,
плотные векторы bge-m3 и BM25 в Qdrant, первый проход bge-reranker и второй проход
генеративной моделью. Сущности и связи проходят второй этап переранжирования вместе
с фрагментами и входят в контекст ответа со ссылками на исходные документы.

Сервисный слой перенесён из `Meno-Stand-RAG-Core` (коммит `a4977e9`). Исходный
production-репозиторий не изменяется и не нужен для запуска нового core.
Исследовательские скрипты остаются в `code/`; их описание приведено ниже.

## Запуск сервера

Основной способ развёртывания — контейнерный стек из соседнего `Meno-Deploy`.
Он включает PostgreSQL, Redis, Qdrant, core, неизменённый Meno-Web, nginx и
при необходимости три GPU-службы моделей. В API-контейнере нет локальной LLM,
FRIDA, FAISS, PyTorch или vLLM: модели вызываются по HTTP. Единый сборщик корпуса
и графа тоже работает в основном CPU-окружении (`uv sync --frozen`). Дополнение
`indexing` требуется только для отдельных исследовательских режимов с локальными
моделями, обходом сайта или построением диаграмм.

Для разработки API без контейнеров:

```bash
uv sync --frozen
cp example.env .env
# Указать адреса уже работающих служб и пути к подготовленной базе знаний.
uv run meno-rag-migrate
uv run meno-rag-api
```

В production нужен PostgreSQL и прежнее значение `AUTH_JWT_SECRET`. Схема БД и
цепочка Alembic сохраняются, автоматического сброса данных нет. Перед переходом
сделайте резервную копию; порядок переноса и возврата описан в `Meno-Deploy/README.md`.

## Ресурсы поиска

Переменная `STAND_RESOURCES_DIR` указывает на каталог со следующими файлами:

```text
data/
  chunked_texts_about_nsu_with_metadata_and_scores.jsonl
  chunk_mapping_to_texts.json
  knowledge/
    abbreviations.json
    ragu_graph/
      knowledge_graph.gml
      kv_chunks.json
      menon_chunk_mapping.json
      qdrant_collections.json
      ...остальные файлы RAGU
```

Коллекции векторов хранятся отдельно в Qdrant. Копирования каталога графа
недостаточно: нужны снимки соответствующих коллекций или повторное индексирование.
`prepare_graph_index.py` теперь сохраняет `qdrant_collections.json` с именами
коллекций. Этот файл позволяет перенести граф в другой каталог без смены
коллекций. Для графа, собранного прежней версией скрипта, создайте JSON с ключами
`vdb_entity`, `vdb_relation`, `vdb_chunk` и фактическими именами коллекций из Qdrant.
Имена нельзя угадывать по новому контейнерному пути.

При старте проверяются координаты фрагментов, отображение RAGU и наличие
непустых коллекций. Если ресурсы не загружены, `/healthz` сообщает `degraded`,
а `/readyz` возвращает 503. Контейнер web ожидает готовности core.
Один процесс API обслуживает несколько пользователей; графовый поиск работает
в отдельном цикле событий с ограничением параллелизма и тайм-аутом. Результаты
переранжирования и графовый контекст принадлежат отдельному запросу.

Для запуска индексирования в контейнере предусмотрен `scripts/index_graph.py`:
он читает те же настройки `Settings`, передаёт ключи дочернему процессу через
окружение и запускает `prepare_graph_index.py` из `code/`. Дополнительные CLI-флаги,
например `--chunk_header title --chunk_header_sources base,news`, передаются дальше.
Скрипту нужен доступ на запись к отдельному каталогу базы знаний. Сам
`prepare_graph_index.py` поддерживает `MENO_INDEX_LLM_KEY` и
`MENO_INDEX_EMBEDDER_KEY` как значения ключей по умолчанию; явные CLI-флаги
сохраняют приоритет.

## Сборка корпуса и графа одной командой

Из корня нового core выполните:

Qdrant должен быть доступен по указанному адресу. Для сборки на хосте с
хранилищем из Meno-Deploy запустите там `./scripts/compose.sh --indexing up -d qdrant`:
этот режим открывает REST-порт на `127.0.0.1:6333` и использует тот же том Qdrant,
к которому подключается контейнер backend. Docker и файлы окружения Deploy
должны быть подготовлены заранее.

```bash
uv run --frozen python scripts/build_knowledge.py \
  --source-url https://disk.yandex.ru/d/XZjLjlah72eG1w \
  --input-dir /home/rsolikhov/meno_stand_actual/data \
  --output-dir /home/rsolikhov/knowledge/nsu-v1 \
  --llm-url http://everest.nsu.ru:9022/v1 \
  --llm-model gemma-4-12B-it \
  --tokenizer google/gemma-4-12B-it \
  --embedder-url http://127.0.0.1:8001/v1 \
  --embedder-tokenizer /home/rsolikhov/vllm/bge-m3 \
  --qdrant-url http://127.0.0.1:6333
```

В примере используется выбранная внешняя модель `gemma-4-12B-it` на Everest.
Пути соответствуют серверу `/home/rsolikhov`; при другом расположении замените их.
Скрипт обращается к уже работающим LLM, bge-m3 и Qdrant; службы и контейнеры он
не запускает. Реранкер при индексировании не используется. LLM должна поддерживать
OpenAI-совместимые chat completions со структурированным JSON-ответом.
Генерация названий и аннотаций, извлечение и проверка сущностей и связей,
а также графовые обобщения используют указанную внешнюю модель. Диалоговую
модель meno-lite-0.1 можно оставить прежней.

`--llm-model` можно опустить, если `/v1/models` возвращает единственную модель;
иначе задайте её имя в API явно. `--tokenizer` — локальный каталог либо HF id
токенизатора, а не псевдоним модели в API. Для этого нужны файлы токенизатора,
веса генеративной модели на машине сборщика не нужны. По умолчанию этим же
токенизатором измеряется контекст графовой LLM. Если корпус нужно разбивать
токенизатором Meno, укажите его в `--tokenizer`, а токенизатор внешней LLM —
в `--graph-tokenizer`. Токенизаторы проверяются до обработки корпуса.

Официальный [токенизатор Gemma 4](https://huggingface.co/google/gemma-4-12B-it/tree/main)
загружается автоматически по HF id. Его текстовый режим поддерживается в
CPU-окружении core с Transformers 4.x; веса Gemma на машине сборщика не нужны.
Окно контекста определяется по `max_model_len` выбранной модели из `/v1/models`.
Если API не сообщает это поле, используется 16384; флаг `--llm-context-tokens`
задаёт предел явно и не может превышать объявленное сервером значение.

Если данные ещё не скачаны, `--source-url` загружает нужные файлы из публичной
папки Яндекс Диска в `--input-dir` перед сборкой. Каталог создаётся автоматически;
для нового каталога в нём сразу появляются `source/` и `knowledge/`. Ссылка может
вести на папку `meno_stand_actual` или непосредственно на её `data`. Если данные
уже скачаны вручную, флаг `--source-url` можно опустить. Для опубликованного
[набора исходников](https://disk.yandex.ru/d/XZjLjlah72eG1w) автоматически выбираются:

- `source/nsu_text_corpus_20260706.jsonl` — подготовленный справочник;
- последний по дате `source/teachers_corpus_YYYYMMDD.jsonl` — преподавателей;
- `source/nsu_text_corpus_20250318_validated.jsonl` — проверенный корпус сайта;
- все `source/filtered_news_YYYYMMDD_YYYYMMDD.jsonl`, включая файл за 9 июля — 16 октября;
- `knowledge/abbreviations.json` — словарь аббревиатур.

В текущем наборе скачиваются восемь файлов общим объёмом около 239 МБ. Полный
исходный обход сайта и сырые профили преподавателей не скачиваются, если есть
подготовленные версии. Если подготовленного справочника или корпуса
преподавателей нет, скрипт создаст их из `nsu_main_info.md` и пары
`source/teachers.json` / `source/teachers_chunks.json`, предварительно скачав их.
Отдельные пути можно
переопределить флагами `--summary`, `--teachers`, `--base`, `--abbreviations`
и повторяемым `--news`. Повторная проверка доступности URL сайта в сборку не входит.

Загрузка идёт через [публичный API Яндекс Диска](https://yandex.cloud/ru/docs/datasphere/operations/data/connect-to-ya-disk).
Готовые файлы проверяются по размеру и SHA-256 и не скачиваются повторно;
незавершённый файл хранится с суффиксом `.part` и после обрыва скачивается заново.
Список файлов и контрольные суммы фиксируются в `--input-dir/.yandex-source.json`:
повторный запуск продолжает тот же набор, даже если содержимое публичной папки
изменилось. Если изменился ещё не скачанный файл, несовпадение SHA-256 остановит
загрузку. Для новой версии набора укажите новый `--input-dir`. Существующие
локальные файлы с другой контрольной суммой не перезаписываются.

Этапы сборки: загрузка исходников (с `--source-url`) → объединение и удаление
дубликатов → разбиение на фрагменты →
подсчёт токенов и фиксация порядка документов → названия и аннотации через LLM →
оценка метаданных через bge-m3 → даты новостей → отображение индексов → граф RAGU
и три векторные коллекции Qdrant. Даты по умолчанию вычисляются в часовом поясе
`Asia/Novosibirsk`; локаль `ru_RU.UTF-8` не требуется. Их добавление отключается
флагом `--no-news-dates`. Диаграммы качества не строятся.

По умолчанию размер фрагмента — 350 токенов, контекст LLM определяется через API, предел
ответа при сборке графа — 6144, параллелизм — 8 запросов, примеры в промптах
отключены. При необходимости измените `--chunk-tokens`, `--llm-context-tokens`,
`--max-completion-tokens`, `--concurrency` и `--icl-examples`; контекст должен
превышать предел ответа. Тексты из источников `base,news` получают заголовок
документа перед извлечением графа (`--chunk-header title`). Все параметры
перечислены в `python scripts/build_knowledge.py --help`.

Перед запросом к графовой LLM сборщик проверяет, помещаются ли промпт и
зарезервированный ответ в заданное окно контекста. Если окно превышено,
результат не публикуется; подробности и необходимые размеры будут в журнале.
Для этой проверки токенизатор внешней модели должен содержать её chat template.

Добавьте `--dry-run`, чтобы проверить выбор файлов и увидеть команды без
HTTP-запросов, загрузки токенизаторов и записи результатов. Если исходников ещё
нет, этот режим выводит этап загрузки и краткий план; точный состав файлов
определяется при настоящем запуске. Рабочие файлы,
поэтапные журналы и кэш ответов графовой модели сохраняются рядом с результатом,
в примере — `/home/rsolikhov/knowledge/.nsu-v1.build/`. После сбоя повторите ту же
команду: завершённые этапы пропускаются после сверки контрольных сумм, генерация
метаданных продолжается с первого незавершённого или ошибочного документа,
а RAGU повторно использует кэш LLM. Промежуточные JSONL с изменённой контрольной
суммой обрабатываются заново; повреждение уже опубликованной базы считается ошибкой.
Изменение исходников, параметров, локальных токенизаторов или кода требует
нового `--output-dir`; существующая база не перезаписывается.

Каталог `--output-dir` появляется после проверки корпуса, отображений и
наличия данных в Qdrant. Он содержит весь набор из раздела «Ресурсы поиска»
и `build_manifest.json` с контрольными суммами и параметрами сборки. Подключите
его как `STAND_RESOURCES_DIR`, а тот же Qdrant — как `QDRANT_URL` backend.
При переносе на другой сервер вместе с файлами нужны снимки коллекций Qdrant.

Ключи LLM и векторизации задавайте переменными `MENO_INDEX_LLM_KEY` и
`MENO_INDEX_EMBEDDER_KEY`; для Qdrant сборщик читает `QDRANT_API_KEY`.
Имена первых двух переменных можно изменить через `--llm-key-env` и
`--embedder-key-env`. Значения ключей не включаются в команды и манифест.

## Длительная сборка в tmux и журналы

После установки `tmux`, `uv` и запуска Qdrant создайте сессию на сервере:

```bash
tmux new-session -s meno-build -c /home/rsolikhov/meno_ragu_stand bash
```

Внутри этой сессии выполните:

```bash
mkdir -p /home/rsolikhov/logs
export PATH="$HOME/.local/bin:$PATH"
set -o pipefail
uv run --frozen python -u scripts/build_knowledge.py \
  --source-url https://disk.yandex.ru/d/XZjLjlah72eG1w \
  --input-dir /home/rsolikhov/meno_stand_actual/data \
  --output-dir /home/rsolikhov/knowledge/nsu-v1 \
  --llm-url http://everest.nsu.ru:9022/v1 \
  --llm-model gemma-4-12B-it \
  --tokenizer google/gemma-4-12B-it \
  --embedder-url http://127.0.0.1:8001/v1 \
  --embedder-tokenizer /home/rsolikhov/vllm/bge-m3 \
  --qdrant-url http://127.0.0.1:6333 \
  --log-level DEBUG \
  2>&1 | tee -a /home/rsolikhov/logs/meno-knowledge-build.log
meno_build_exit=${PIPESTATUS[0]}
printf '\nКод завершения сборщика: %s\n' "$meno_build_exit" | tee -a /home/rsolikhov/logs/meno-knowledge-build.log
```

Вывод stdout и stderr одновременно виден в tmux и сохраняется в общий файл.
`--log-level DEBUG` включает подробные сообщения RAGU; параметр можно менять
при продолжении сборки, не пересоздавая результаты. Python работает без
буферизации. Поэтапные журналы в `.nsu-v1.build/logs/` дополняются при повторных
попытках и содержат время запуска каждого этапа. Код завершения `0` означает
успешную сборку; другой код нужно проверять по журналу.

Для отключения нажмите **Ctrl+B**, отпустите клавиши, затем **D**. Сборка
продолжится после отключения SSH. Для возвращения используйте
`tmux attach-session -t meno-build`; просмотр истории — **Ctrl+B**, затем **[**,
выход из просмотра — **Q**. Из другого SSH-сеанса журнал можно читать командой:

```bash
tail -n 100 -F /home/rsolikhov/logs/meno-knowledge-build.log
```

Сессия переживает отключение SSH, но не перезагрузку сервера. После перезагрузки
повторите команду сборки в новой сессии: сохранённые этапы и кэш будут использованы
для продолжения. Управление сессиями описано в [руководстве tmux](https://man.openbsd.org/tmux.1).

## Настройки

| Переменная | Назначение |
| --- | --- |
| `DATABASE_URL`, `REDIS_URL` | Хранение и блокировки арены |
| `AUTH_JWT_SECRET` | Секрет существующей авторизации; сохранить при переносе |
| `STAND_RESOURCES_DIR`, `RAGU_GRAPH_DIR` | Каталог корпуса и необязательное переопределение пути графа |
| `QDRANT_URL` | Адрес Qdrant, содержащего коллекции графа |
| `EMBEDDER_MODEL`, `EMBEDDER_URL`, `EMBEDDER_API_KEY` | Служба bge-m3; модель должна совпадать с использованной при индексировании |
| `ENGINE_RERANKER_MODEL`, `ENGINE_RERANKER_URL`, `ENGINE_RERANKER_API_KEY` | Первый этап переранжирования; пустое имя отключает этап |
| `VLLM_ENDPOINTS` | Адреса служб генерации через запятую; допустим суффикс `/v1` |
| `OPENAI_API_KEY` | Общий ключ служб генерации и обнаружения моделей |
| `VLLM_ENDPOINT_API_KEYS` | JSON-словарь отдельных ключей по адресу службы; пустое значение ключа отключает Authorization для этого адреса |
| `RAG_REWRITE_RERANK_MODEL` | Локальная модель для переписывания и второго этапа переранжирования |
| `GRAPH_TOP_K`, `TOP_K`, `ENGINE_RERANK_TOP_K` | Размеры выдач графового поиска и первого этапа |
| `RERANK_CANDIDATES_PER_QUERY`, `RERANK_TOP_K`, `MAX_CONTEXT_CHUNKS` | Ограничения смешанного пула и контекста |
| `GRAPH_TIMEOUT_SECONDS`, `EMBED_CONCURRENCY` | Тайм-аут и число одновременных графовых запросов |
| `BENCH_API_TOKEN` | Отдельный режим измерений без записи диалогов в production-таблицы |

Графовые элементы учитываются в общем ограничении `MAX_CONTEXT_CHUNKS`.
Исторические значения базы знаний `nsu-stand-faiss-bm25` принимаются при
восстановлении старого диалога; новая выдача использует `nsu-ragu`, чтобы
результаты арены с разными способами поиска не смешивались.
Механизм подбора примеров ответов из старого core в новом конвейере отключён.

```bash
uv run pytest -q
```

собирает образ core. Проверка на реальной видеокарте выполняется на Linux-сервере.

# Стендовая версия системы «Менон»

Код для «стендовой» (не продовой) версии диалоговой системы «Менон», предназначенной для экспериментов с различными компонентами RAG-конвейера

## 1 Структура каталогов проекта

1. Каталог `code` — весь код проекта: python-скрипты, модули и вспомогательные bash-скрипты (запуск полного индексирования, проброс туннелей); в подкаталоге `code/slurm` лежат задания SLURM для GPU-кластера «Каскад».
   
2. Каталог `data` — здесь лежат исходные данные проекта; также сюда надо складывать дополнительные данные, генерируемые в ходе экспериментов (как текстовые в форматах `*.json` и `*.jsonl`, так и бинарные):

    - подкаталог `data/source` — исходные данные в формате `*.jsonl`, скачанные с основного сайта НГУ и с университетских групп в соцсетях, а также JSON-файлы `teachers.json` и `teachers_chunks.json` со сведениями о преподавателях и сотрудниках НГУ и подготовленный из них скриптом `prepare_teachers_corpus.py` файл `teachers_corpus_*.jsonl`;

    - подкаталог `data/knowledge` — сюда сохранять поисковые индексы базы знаний: граф знаний RAGU (подкаталог `ragu_graph`) вместе с дисковым кэшем ответов генеративной модели; векторные хранилища графа размещаются в Qdrant; там же лежит словарь аббревиатур `abbreviations.json` (обязательный вход диалоговых скриптов, флаг `-a`); словарь подготавливается вне репозитория;
    - подкаталог `data/fewshots` — наборы оценочных диалоговых данных (в подкаталоге `source` — сторонние наборы данных для оценки поиска); используются как образцы входных данных, например для `show_dialogue_history.py` (раздел 5.1);
    - основной каталог `data/.` — сюда сохранять `*.jsonl` файлы с различными стадиями постобработки исходных данных (под стадиями постобработки понимается разбиение документов на фрагменты, составление их аннотаций и т.п.) и `*.json` файл с отображением глобальных индексов фрагментов в их «локальные» координаты (номер документа и номер фрагмента в документе).

3. Каталог `pictures` — сюда надо складывать научно-технические иллюстрации, генерируемые в ходе экспериментов.

4. Файл `interesting_to_students.md` в корне проекта — исходный материал (опрос интересов студентов), использовавшийся при составлении справочника `data/nsu_main_info.md`.

## 2 Подготовка окружения и служб

### 2.1 Установка пакетов

Нужен Python не младше 3.10. Рекомендуемый способ — отдельное conda-окружение:

```bash
conda create -n meno python=3.10 -y
conda activate meno
pip install graph_ragu sentence-transformers nltk razdel openai pydantic tqdm pytest
```

Пакет `graph_ragu` устанавливает библиотеку RAGU (в коде импортируется как `ragu`), а вместе с ней — `qdrant-client` и `fastembed` (встроенная модель BM25 для лексического канала поиска). Остальные пакеты ставятся по потребности:

- `vllm`, `torch`, `transformers` — для офлайн-режима `--vllm` и для самостоятельного запуска служб генерации, векторизации и оценки;
- `crawl4ai`, `pymupdf` — только для скрипта обхода сайта `crawl_nsu_for_kb.py` (раздел 3.10);
- `urllib3`, `certifi` — только для скрипта проверки ссылок `validate_base_urls.py` (раздел 3.3).

Данные для русского стеммера Snowball входят в современные версии пакета `nltk` и отдельно не скачиваются.

### 2.2 Службы, необходимые демонстрационным скриптам

Модельные компоненты работают как службы с OpenAI-совместимым интерфейсом. Состав служб зависит от скрипта:

| Скрипт | Службы | Прочие данные |
|---|---|---|
| тесты (`python -m pytest`, раздел 7) | не нужны | не нужны |
| `show_dialogue_history.py` (раздел 5.1) | не нужны | образец из `data/fewshots` |
| `show_context_by_chunks.py` (раздел 5.3) | не нужны | корпус и отображение индексов |
| `show_question_rewriting.py` (раздел 5.2) | генеративная модель | словарь аббревиатур |
| `search_context_by_query.py` (раздел 4) | векторизация, Qdrant, оценка реранкера; генеративная модель — только при `--reranker` | корпус, отображение индексов, граф |
| `chat.py` (раздел 6) | векторизация, Qdrant, генеративная модель, оценка реранкера | корпус, отображение индексов, граф, словарь аббревиатур |
| `prepare_graph_index.py` (раздел 3.13) | векторизация, Qdrant; генеративная модель — кроме `--vector_only` | корпус, отображение индексов |

Пример запуска служб на одной машине (порты 8000–8002 условны; во флагах скриптов адрес и ключ службы генерации по умолчанию — `http://localhost:8000/v1` и `EMPTY`):

```bash
vllm serve bond005/meno-lite-0.2 --port 8000
vllm serve BAAI/bge-m3 --task embed --port 8001
vllm serve BAAI/bge-reranker-v2-m3 --port 8002
```

Флаги могут отличаться между версиями vLLM; для службы оценки нужен эндпоинт `score`, который открывают серверы в стиле vLLM и Infinity (см. документацию библиотеки RAGU). Модель bge-m3 (около 4,6 ГБ весов) при первом запуске скачивается из HF Hub в локальный кэш. Вместо службы генеративная модель может запускаться офлайн-режимом `--vllm` прямо в скриптах; для этого нужна видеокарта на той же машине. Первый проход переранжирования в `chat.py` и `search_context_by_query.py` включён по умолчанию (значение `--engine_reranker` по умолчанию — `BAAI/bge-reranker-v2-m3`), поэтому служба оценки нужна этим скриптам сразу; пустое значение флага (`--engine_reranker ""`) отключает первый проход и снимает потребность в службе оценки.

### 2.3 Qdrant

Векторные коллекции графа хранятся в Qdrant. Для демонстраций и ручного тестирования сервер запускается одним из способов:

```bash
# одиночный бинарник (скачан с https://github.com/qdrant/qdrant/releases)
./qdrant
# либо контейнер
docker run -d -p 6333:6333 -v qdrant_storage:/qdrant/storage qdrant/qdrant
```

Режимы векторного хранилища, поддерживаемые библиотекой `qdrant-client` (задаются флагом `--qdrant_location`):

- адрес сервера — основной режим: граф собирается один раз, затем запрашивается из других сеансов и скриптов;
- `:memory:` — встроенный режим в памяти процесса; данные не переживают завершение процесса, поэтому режим пригоден только для одноразовых экспериментов и тестов (так устроен интеграционный тест);
- локальное хранилище на диске — допускает только одного клиента на каталог, поэтому из трёх векторных хранилищ RAGU (сущности, связи, фрагменты) в нём сосуществует лишь одно; режим пригоден только для сборки `--vector_only`.

Расположение Qdrant должно совпадать при сборке графа и при поиске.

## 3 Как создать базу знаний из исходных данных

>  **Примечание:** установка пакетов и запуск служб описаны в разделе 2; запуск всех скриптов, описанных ниже, надо делать не из корня проекта, а из каталога `code` (он должен быть текущим при запуске).

### 3.1 Шаг первый: формирование сводного исходного JSONL-файла из единого справочника об НГУ

Сводный исходный JSONL-файл базы знаний (тот, что подаётся на флаг `-s` скрипта `combine_data.py` на следующем шаге) удобнее всего получать не прямой выкачкой страниц сайта НГУ, а из заранее подготовленного единого человеко-ориентированного справочника `data/nsu_main_info.md`. Этот справочник составлен по материалам официального сайта НГУ (в первую очередь — раздела «Часто задаваемые вопросы» и нормативных документов раздела «Сведения об образовательной организации») с упором на реальные вопросы абитуриентов, студентов и аспирантов.

Для преобразования единого справочника в набор самодостаточных текстовых элементов (будущих документов RAG-системы) служит python-скрипт `prepare_nsu_main_info_corpus.py`. Аргументы командной строки:

- `-i` (или `--input`): путь к исходному файлу-справочнику (`data/nsu_main_info.md`);
- `-o` (или `--output`): путь к создаваемому сводному JSONL-файлу базы знаний;
- `--min_chars` (необязательный): минимальный размер самостоятельного документа в символах; более короткие вводные абзацы разделов автоматически присоединяются к первому дочернему подразделу (по умолчанию 250);
- `--max_chars` (необязательный): порог для предупреждения о слишком крупном документе (по умолчанию 12000).

Скрипт разбирает Markdown-структуру справочника и формирует документы по **большим разделам** (`##`): как правило, один раздел — один документ. **Исключение** составляет раздел «Институты и факультеты» — он по своей природе объединяет 13 независимых учебных подразделений, поэтому дробится по подразделам (`###`), и каждый факультет/институт становится отдельным документом (это даёт более точные названия и аннотации на последующих шагах конвейера). Каждый документ снабжается самодостаточной шапкой-контекстом вида `**Новосибирский государственный университет (НГУ). <раздел>.**` (для факультетов — `… . <раздел>. <подраздел>.**`), так что он понятен без чтения остальных; внутренние подзаголовки раздела (`###`, `####`) при этом преобразуются в жирные строки. Markdown-таблицы преобразуются в обычный текст: каждая строка таблицы становится отдельным абзацем, в котором «человеческим языком» перечислены значения всех ячеек с упоминанием заголовков столбцов и общего названия таблицы (название дублируется для каждой строки, а единицы измерения раскрываются — например, `руб./мес.` превращается в «рублей в месяц»). Поскольку каждый раздел-документ обобщает информацию с разных веб-страниц, поле `url` собирает **все** уникальные веб-ссылки документа, отсортированные по приоритету (тематические страницы `nsu.ru/n/…` и `education.nsu.ru/…` предпочтительнее PDF-приказам).

Каждая строка выходного JSONL-файла — это словарь вида `{"text": "строка", "url": ...}`, где поле `url` может быть **строкой** (если источник один) или **списком строк** (если документ обобщает несколько веб-страниц). Такое полиморфное представление `url` (строка ИЛИ список) поддерживается на всех последующих шагах конвейера (в `combine_data.py`, `context_utils` и др.) через единый хелпер нормализации `normalize_urls`, поэтому файлу сводного справочника (где `url` часто список) и файлу обходчика (где `url` всегда строка) можно давать на вход `combine_data.py` — каждый через свой флаг (`-s` и `-b` соответственно).

Пример вызова python-скрипта `prepare_nsu_main_info_corpus.py`:

```bash
python prepare_nsu_main_info_corpus.py -i ../data/nsu_main_info.md -o ../data/source/nsu_text_corpus_20260706.jsonl
```

### 3.2 Шаг второй: подготовка исходного JSONL-файла о преподавателях и сотрудниках НГУ

Сведения о преподавателях и сотрудниках НГУ хранятся в двух JSON-файлах подкаталога `data/source`:

- `teachers.json` — полные структурированные данные по каждому человеку: ФИО, сокращённое ФИО, универсальный идентификатор, ссылка на расписание занятий, само расписание (день недели, время, тип занятия, дисциплина, аудитория, учебные группы), сведения о работе (должность, подразделение, учёная степень, стаж, перечень дисциплин и образовательных программ), а также данные портала НГУ (адрес электронной почты, направления исследований, публикации с аннотациями);
- `teachers_chunks.json` — те же сведения, заранее разбитые на самодостаточные текстовые фрагменты в формате Markdown; каждая запись содержит список фрагментов, а первый фрагмент каждой записи начинается заголовком `# <ФИО>` и включает разделы «Основные сведения», «Расписание» и «Направления работы»; последующие фрагменты содержат публикации частями.

Записи двух файлов выровнены по индексам: запись с номером i первого файла соответствует записи с номером i второго файла. Скрипт `prepare_teachers_corpus.py` проверяет это соответствие по ФИО и формирует JSONL-файл, в котором каждый текстовый фрагмент становится самостоятельным документом с полем `url`, равным ссылке на расписание преподавателя.

Аргументы командной строки:

- `-i` (или `--input`): путь к файлу `teachers.json`;
- `-c` (или `--chunks`): путь к файлу `teachers_chunks.json`;
- `-o` (или `--output`): путь к создаваемому JSONL-файлу;
- `--include_empty_schedule` (необязательный): включить в выдачу и тех людей, у которых расписание занятий пустое. По умолчанию в базу знаний попадают только преподаватели, ведущие занятия в текущем семестре.

Пример вызова python-скрипта `prepare_teachers_corpus.py`:

```bash
python prepare_teachers_corpus.py -i ../data/source/teachers.json -c ../data/source/teachers_chunks.json -o ../data/source/teachers_corpus_20261019.jsonl
```

### 3.3 Шаг третий: объединение исходных файлов в общий JSONL

Для этого нужно запустить python-скрипт `combine_data.py` со следующими аргументами командной строки:

- `-s` (или `--summary`): **сводный исходный JSONL-файл** — авторитетный, курируемый справочник о НГУ, полученный из единого документа `data/nsu_main_info.md` (такой файл может быть только один);
- `-t` (или `--teachers`): **исходный JSONL-файл о преподавателях и сотрудниках НГУ**, подготовленный скриптом `prepare_teachers_corpus.py` на предыдущем шаге (такой файл может быть только один). Записи этого файла записываются в объединённый результат сразу после сводного справочника и не проходят ни дедубликацию, ни фильтрацию по длине текста, ни обратный индекс дубликатов;
- `-b` (или `--base`): **дополнительный исходный JSONL-файл** с данными, полученными программой автоматического обхода основного сайта НГУ (такой файл может быть только один). Перед подачей на `-b` файл **можно** предварительно отфильтровать с помощью скрипта `validate_base_urls.py` (см. ниже), который удаляет записи с некорректным содержимым (пустой текст, ошибки HTTP-серверов, слишком короткие тексты) и с мёртвыми ссылками.
- `-n` (или `--news`): **исходные JSONL-файлы с новостями** об НГУ, скачанными с университетских соцсетей (таких файлов может быть много, сколько угодно, и предполагается, что названия таких файлов всегда имеют суффикс вида `*_yyyymmdd_yyyymmdd.jsonl`, в котором закодирован временной период получения новостей об НГУ с начальной даты dd.mm.yyyy до конечной даты dd.mm.yyyy);
- `-o` (или `--output`): **результат объединения всех файлов** с исходными данными в единую структуру «документ - веб-ссылка - тип источника (сводный справочник, основной сайт НГУ или новости)».

Каждая строка сводного JSONL-файла (`-s`) — это словарь вида `{"text": "строка", "url": ...}`, где поле `url` может быть строкой или списком строк. Сводные документы записываются в объединённый результат первыми и **не участвуют в дедубликации** — ни против новостей, ни против файла обходчика. Пример:

```json lines
{"text": "**Новосибирский государственный университет (НГУ). Общие сведения о НГУ.**\n\n**Полное наименование:** Федеральное государственное автономное образовательное учреждение высшего образования «Новосибирский национальный исследовательский государственный университет».\n...", "url": ["https://www.nsu.ru/n/university/", "https://www.nsu.ru/n/sveden/"]}
```

Каждая строка файла обходчика (`-b`) — это словарь вида `{"text": "строка", "url": "строка"}`, например:

```lines
{"text": "```\nВ 2014 году силами факультета психологии НГУ и инициативной группы родителей был создан научно-практический центр, осуществляющий поддержку семей с детьми с особенностями развития. Специалисты Центра помогают семьям в решении проблем коррекции и развития детей через комплексный подход. Методы работы для каждого ребенка подбираются индивидуально.\n\n\n\n**Курс \"АВА-инструктор\" 2026 стартует в феврале. Подробности\n\n\n\nНГУ г. Новосибирск, ул. Пирогова 1,\n\n+7 (383) 363-43-78\n\n+7-905-955-43-78\n\naba@nsu.ru\n**\n```\n\n", "url": "http://aba.nsu.ru/"}
```

В словаре, описывающем строку файла обходчика (`-b`), могут быть дополнительные ключи, помимо `text` и `url`, но они будут проигнорированы.

Каждая строка любого из дополнительных исходных JSONL-файлов — это словарь вида `{"url": "строка", "content": "строка"}`, например:

```lines
{"url": "https://vk.com/wall-37080997_43976", "name": "Новосибирский государственный университет | НГУ", "content": " НГУ приглашает на День открытых дверей! Приемная кампания — близко, поэтому не упусти возможность погрузиться в атмосферу университета, поймать студенческий вайб, посмотреть на новый кампус мирового уровня и, конечно, узнать, чего ждать абитуриенту в этом году. Логика объединения записей из всех исходных файлов в общую базу документов такова:
```

- **справочник** (`-s`): читаются записи сводного JSONL-файла, и каждая такая запись добавляется в объединённый результат целиком (без дедубликации и без фильтрации по длине текста), с `content_source` = `summary`. Сводные записи записываются первыми и имеют наивысший приоритет при последующей индексации;
- **преподаватели** (`-t`): читаются записи JSONL-файла о преподавателях и сотрудниках, и каждая такая запись добавляется в объединённый результат без фильтрации и дедубликации, с `content_source` = `teachers`, сразу после сводного справочника;
- все новостные файлы сортируются по убыванию «свежести» (а «свежесть» определяется по обязательному суффиксу в названиях файлов — так, файл `filtered_news_20260306_20260403.jsonl` содержит более «свежие» данные, чем файл `filtered_news_20260220_20260306.jsonl`);
- читаются записи каждого из отсортированных новостных файлов, и очередная запись добавляется в объединённый результат только в том случае, если она состоит не менее чем из 10 слов и если её url и/или текст не были ранее добавлены (эта проверка даёт дедубликацию записей в объединённом результате и отсекает «мусорные» обрывки текста);
- читаются записи файла обходчика (`-b`), и каждая такая запись добавляется в общую базу документов только если текст не слишком короткий (содержит не менее чем 10 слов), не является «плохим» (некорректно выкачанным из интернета, то есть таким, в котором нет ничего типа «страница не найдена») и не дублирует тексты, ранее добавленные в объединённую базу документов (включая новости и уже обработанные записи обходчика), более чем на 90% слов (для быстрой проверки таких вот «нечётких» дубликатов автоматически строится обратный индекс документов по словам).

Отброшенные записи не печатаются в журнал: по завершении скрипт выводит сводную статистику — сколько текстов отклонено как пустые, дубликаты и некачественные.

Пример вызова python-скрипта `combine_data.py`:

```bash
python combine_data.py -s ../data/source/nsu_text_corpus_20260706.jsonl -t ../data/source/teachers_corpus_20261019.jsonl -b ../data/source/nsu_text_corpus_20250318.jsonl -n ../data/source/filtered_news_20260220_20260306.jsonl -n ../data/source/filtered_news_20260306_20260403.jsonl -o ../data/united_texts_about_nsu.jsonl
```

**(Необязательно)** Перед запуском `combine_data.py` файл обходчика (`-b`) можно предварительно отфильтровать с помощью скрипта `validate_base_urls.py`, который проверяет содержимое записей и доступность ссылок:

```bash
python validate_base_urls.py -i ../data/source/nsu_text_corpus_20250318.jsonl -o ../data/source/nsu_text_corpus_20250318_filtered.jsonl --concurrency 500 --timeout 15 --max-per-host 10
```

Скрипт выполняет трёхфазную фильтрацию: (1) проверка текста (пустые тексты, фразы-индикаторы ошибок, слишком короткие тексты — мгновенно), (2) параллельная HTTP-проверка URL'ов через `urllib3` с пулом соединений (автоматическое percent-кодирование non-ASCII URL, ограничение числа одновременных соединений на каждый хост через `--max-per-host`, учёт редиректов, повторные попытки, прогресс-бар `tqdm`), (3) удаление записей, у которых **все** ссылки мёртвые. Результат — отфильтрованный JSONL-файл, который подаётся на `-b`.

### 3.7 Шаг седьмой: оценка качества сгенерированных метаданных относительно исходных документов

HTTP-режим не требует PyTorch или локальной модели. Ключ по умолчанию читается
из `MENO_INDEX_EMBEDDER_KEY`.

Скрипт оценивает близость названия и аннотации документа к тексту его первых фрагментов в векторном пространстве модели bge-m3 и записывает итоговую оценку качества в поле `quality_score` каждой записи. Предусмотрены два режима. Со службой векторизации (основной режим, используется драйвером `index_kb.sh`; удобно, когда служба уже поднята, например для сборки графа): флаг `-m` задаёт имя модели, как его видит служба, а `--url` и `--key` — адрес и ключ службы с OpenAI-совместимым интерфейсом.

```bash
python -u evaluate_title_and_annotation.py -i ../data/chunked_texts_about_nsu_with_metadata.jsonl -o ../data/chunked_texts_about_nsu_with_metadata_and_scores.jsonl -m BAAI/bge-m3 --url http://localhost:8001/v1 --minibatch 32
```

Без флага `--url` модель загружается локально как `SentenceTransformer`, и флаг `-m` принимает локальный путь или идентификатор с Hugging Face:

```bash
python -u evaluate_title_and_annotation.py -i ../data/chunked_texts_about_nsu_with_metadata.jsonl -o ../data/chunked_texts_about_nsu_with_metadata_and_scores.jsonl -m /home/bond005/models/bge-m3 --minibatch 32
```

В обоих режимах векторы приводятся к единичной длине перед вычислением расстояний, поэтому шкала оценок сохраняется. Оценки, полученные на разных моделях векторных представлений, несопоставимы между собой: при смене модели шаг выполняется заново, и порог `--min_quality` в поисковых скриптах подбирается под новую шкалу оценок. Оценки, полученные на одной и той же модели разными режимами, совпадают с точностью до численных различий обслуживания; после пересборки базы знаний порог `--min_quality` стоит сверить по гистограммам шага восьмого.

### 3.10 (Необязательно) Автоматический обход сайта НГУ для формирования файла `-b`

Скрипт `crawl_nsu_for_kb.py` выполняет автоматический обход сайта НГУ и готовит файл для флага `-b` скрипта `combine_data.py`. Для работы нужны библиотеки `crawl4ai` (обход и очистка страниц) и `pymupdf` (извлечение текста из документов PDF).

Обход состоит из двух частей: проход по заранее составленным спискам стартовых страниц, сгруппированных по темам (общие сведения, поступление, факультеты, кампус, спорт, студенческие клубы и другие), и глубокий обход в ширину от корневых страниц факультетов с ограничением по домену и по шаблонам адресов. Текст страницы очищается от навигационных элементов фильтром по информативности. Ссылки на документы PDF скачиваются, их текст извлекается и добавляется к результатам обхода.

Аргументы командной строки:

- `-o` (или `--output`): каталог для записи результатов (по умолчанию `/tmp/opencode/nsu_crawl`);
- `--mode`: состав обхода, одно из трёх значений: `curated` (только списки стартовых страниц), `deep` (только глубокий обход), `all` (оба вида, значение по умолчанию);
- `--deep_max_pages`: предельное число страниц на один корень глубокого обхода (по умолчанию 12);
- `--deep_time_budget`: предельная длительность фазы глубокого обхода в секундах (по умолчанию 600);
- `--pdf_budget`: предельное число обрабатываемых документов PDF (по умолчанию 100).

Результаты записываются в два файла. Файл `pages.jsonl` содержит записи вида `{"url", "title", "topic", "source_type", "text"}`; дополнительные ключи `combine_data.py` игнорирует, поэтому файл допускается подавать прямо на флаг `-b` (при необходимости его можно сначала отфильтровать скриптом `validate_base_urls.py`, см. шаг третий). Файл `summary.json` содержит сводную статистику обхода.

Пример вызова:

```bash
python crawl_nsu_for_kb.py -o ../data/source/nsu_crawl_20261002 --mode all
```

### 3.11 (Необязательно) Дополнение названий новостей датой публикации

После седьмого шага конвейера названия документов можно дополнить датой публикации новости. ```

### 3.12 Построение отображения глобальных индексов фрагментов

Скрипт `prepare_chunk_mapping.py` создаёт файл `data/chunk_mapping_to_texts.json`: отображение глобальных индексов фрагментов в их «локальные» координаты (индекс документа и индекс фрагмента внутри документа). Этот файл обязателен для сборки графа знаний и для всех диалоговых скриптов (флаг `-r`). Фрагменты нумеруются сквозной нумерацией по порядку документов во входном файле и по порядку границ в поле `chunks` каждого документа.

Аргументы командной строки:

- `-i` (или `--input`): JSONL-файл базы знаний с границами фрагментов (поле `chunks` появляется после пятого шага конвейера);
- `-o` (или `--output`): создаваемый JSON-файл отображения.

Пример вызова:

```bash
python prepare_chunk_mapping.py -i ../data/chunked_texts_about_nsu_with_metadata_scores_and_news_dates.jsonl -o ../data/chunk_mapping_to_texts.json
```

Скрипт проверяет непустоту текста каждого фрагмента и завершается ошибкой, если найден пустой. Порядок документов фиксируется на пятом шаге конвейера: `calculate_num_tokens.py` сортирует документы по числу токенов, а последующие шаги (генерация метаданных, оценка качества, даты новостей) этот порядок сохраняют. Поэтому отображение строят по финальному файлу базы знаний, после всех его изменений, непосредственно перед сборкой графа.

### 3.13 (Необязательно) Построение графа знаний для поиска в режимах local и naive

`--log_level DEBUG` включает подробные журналы RAGU: запросы к моделям,
использование кэша и операции сборки. По умолчанию выбран `INFO`. В едином
сборщике соответствующий параметр называется `--log-level`.

Имя LLM в API и её токенизатор можно разделить: `--llm` задаёт имя в API,
`--llm_tokenizer` — локальный путь или HF id токенизатора. Аналогично работают
`-e` и `--embedder_tokenizer`. Пределы задают `--llm_context_tokens` (по умолчанию
16384) и `--embedder_tokens` (8192). `--qdrant_key` по умолчанию берётся из
`QDRANT_API_KEY`. Эти параметры доступны и через единый сборщик выше.

Поисковым механизмом системы «Менон» служит граф знаний RAGU (репозиторий `https://github.com/RaguTeam/RAGU`, устанавливается командой `pip install graph_ragu` или в виде локального клона; в коде используется как пакет `ragu`). По одному переписанному поисковому запросу выполняются два режима RAGU:

- **local** (поиск по окрестности графа): для запроса отбираются наиболее близкие по векторному представлению сущности, из графа извлекаются их связи, саммари сообществ и исходные фрагменты;
- **naive** (гибридный поиск по фрагментам): плотный векторный поиск по фрагментам (bge-m3) дополняется лексическим поиском BM25, обе выдачи сливаются взвешиванием взаимных рангов (reciprocal rank fusion) на стороне Qdrant.

Модельные компоненты работают как OpenAI-совместимые службы (адаптеры `EmbedderOpenAI` и `ScorerOpenAI` библиотеки RAGU); команды запуска служб приведены в разделе 2.2:

- генеративная модель Meno: извлечение сущностей и связей при сборке графа, переписывание вопросов, переранжирование и генерация ответов в диалоге;
- модель векторных представлений bge-m3: плотные векторы сущностей, связей и фрагментов;
- модель переранжирования bge-reranker-v2-m3: первый проход переранжирования внутри поисковых движков (эндпоинт `score`).

Лексический канал обслуживается локальной моделью BM25 из состава fastembed (пакет ставится вместе с `graph_ragu`): русский стеммер Snowball и русский список стоп-слов выбираются по языку `russian`.

Разреженные и плотные векторы хранятся в Qdrant; режимы хранилища и способы запуска Qdrant описаны в разделе 2.3. Для полного графа (с сущностями и связями) применимы адрес сервера и режим `:memory:`; локальное хранилище на диске допускает только одного клиента на каталог, поэтому из трёх векторных хранилищ RAGU в нём сосуществует лишь одно, и режим пригоден только для сборки `--vector_only`.

Скрипт `prepare_graph_index.py` принимает финальный корпус базы знаний, воспроизводит точные границы его фрагментов (каждый фрагмент базы знаний становится вершиной-документом графа с тем же содержимым и тем же идентификатором) и сохраняет граф с векторными хранилищами. Извлечение сущностей и связей выполняет `TwoStageArtifactsExtractorLLM`: сначала извлекаются сущности, затем для каждой пары сущностей фрагмента — связи. Промпты RAGU используются на русском языке (`Settings.language = "russian"`), извлечённые сущности типизируются по онтологии NEREL. Экстракция по полному корпусу (около 300 тысяч фрагментов) требует сотен тысяч обращений к генеративной модели; такой расчёт занимает много часов непрерывной работы службы генерации и запускается как офлайн-задача (например, на GPU-кластере). Ответы модели кэшируются на диске (флаг `--cache`), поэтому после перезапуска расчёт продолжается с высокой скоростью: уже полученные ответы не запрашиваются повторно.

Аргументы командной строки:

- `-i`: JSONL-файл базы знаний (результат седьмого шага конвейера);
- `-r`: JSON-файл с отображением глобальных индексов фрагментов;
- `-o`: каталог для графа (по умолчанию `../data/knowledge/ragu_graph`);
- `--sources`: список источников через запятую (по умолчанию участвуют все: `summary`, `teachers`, `news`, `base`);
- `--chunk_header` (`none`): контекстное обогащение фрагментов графа; значение `title` добавляет в начало текста каждого фрагмента шапку с названием документа вида `**Документ:** <название>.`, значение `title_annotation` — ещё и строку `**Аннотация:** <аннотация>.`; рекомендуемое значение — `title`;
- `--chunk_header_sources`: список источников, фрагменты которых обогащаются шапкой (по умолчанию обогащаются все); рекомендуемое значение `base,news`: сводный справочник самодостаточен, его шапки и так входят в тексты документов;
- `-a` (или `--abbr`): путь к JSON-словарю аббревиатур; фрагменты, содержащие аббревиатуры из словаря, перед извлечением артефактов переписываются моделью (расшифровка по контексту, остальной текст дословно); переписывание принимается формальной проверкой: длина переписанного текста не меньше 0,6 исходной и не больше суммы исходной длины и ожидаемой стоимости расшифровок, расстояние Левенштейна между исходным и переписанным текстом не превышает той же стоимости, а в тексте остался след расшифровки, нечувствительный к словоизменению (стемминг Snowball); ожидаемая стоимость расшифровок складывается по числу вхождений каждой аббревиатуры, а к верхней границе длины и к границе расстояния добавляется допуск `max(48, 10 % исходной длины)`; при нарушении любого условия используется исходный фрагмент; база знаний хранит исходные тексты фрагментов, а переписанные копии наследуют их идентификаторы, поэтому привязка артефактов к фрагментам не нарушается; без флага этап пропускается;
- `-e` (или `--embedder`): имя модели векторных представлений в службе векторизации, например `BAAI/bge-m3` (обязательный);
- `--embedder_url` и `--embedder_key`: адрес и ключ службы векторизации; если не заданы, используются значения `--url` и `--key`;
- `--llm`: имя генеративной модели, как оно видно службе генерации (обязателен без `--vector_only`);
- `--url` (`http://localhost:8000/v1`) и `--key` (`EMPTY`): адрес и ключ службы генерации с OpenAI-совместимым интерфейсом;
- `--qdrant_location`: расположение Qdrant: адрес сервера, `:memory:` или пустая строка (по умолчанию) для локального хранилища на диске внутри каталога графа (см. раздел 2.3);
- `--vector_only`: построить только векторный контекст фрагментов, без извлечения сущностей и связей; такой граф поддерживает только режим naive и не требует генеративной модели (быстрый способ проверить интеграцию);
- `--cache`: каталог дискового кэша ответов модели (по умолчанию `<каталог графа>/llm_cache`);
- `--rate_max_simultaneous` (8), `--rate_max_per_minute` (0, без ограничения) и `--rate_min_delay` (0, без задержки): ограничители частоты обращений к службе генерации;
- `--temperature` (0.0): температура сэмплирования запросов извлечения и валидации; нулевое значение по умолчанию задаёт детерминированное жадное декодирование;
- `--max_completion_tokens` (4096): предельное число генерируемых токенов на один запрос; ограничивает «бегущие» выдачи на JSON-схемах с открытыми списками;
- `--icl_examples` (2): число примеров in-context learning (подстановки в промпт отобранных примеров извлечения) для экстрактора; 0 отключает;
- `--no_validation`: отключить проверку типов сущностей и связей при извлечении;
- `--no_clustering`: отключить кластеризацию сущностей перед их обобщением;
- `--no_community_summary`: отключить составление саммари сообществ;
- `--max_chunks`: включить в граф не более заданного числа фрагментов (для пробных запусков);
- `--seed` (42): случайное зерно.

Обогащение фрагментов названиями документов передаёт в текст каждого фрагмента глобальный контекст его документа: экстрактор артефактов видит фрагмент вместе с названием документа и составляет более точные определения извлечённых сущностей и связей, чем по «голому» фрагменту. Шапка входит в текст фрагмента, по которому вычисляется его идентификатор, и в промпты извлечения сущностей и связей, поэтому формат шапки заморожен: смена формата меняет идентификаторы всех фрагментов и требует полной пересборки графа с повторным извлечением.

Экстрактор дополнительно приводит варианты имени сущности, различающиеся регистром, пробелами, знаками пунктуации и буквой «ё», к одному написанию: самое частое исходное написание очищается от пунктуации по краям и становится каноническим, а концы связей пересобираются, поэтому последующая группировка RAGU сливает такие дубликаты в одну вершину (например, «НГУ.» и «НГУ» — одна сущность). Ни расшифровка аббревиатур, ни приведение имён не меняют тексты фрагментов в базе знаний: переписанные копии используются только на входе стадий извлечения.

Скрипт завершается ошибкой, если после сборки в графе нет ни одной сущности и ни одной связи: так проявляется гибель службы генерации в середине работы, и пустая база не выдаётся за готовую.

На вырожденных фрагментах (страницы-заготовки, служебные страницы порталов) модель может упереться в потолок генерируемых токенов, не завершив вывод: в журнале появляется предупреждение `LengthFinishReasonError`, и такой фрагмент остаётся без извлечённых артефактов. Сам фрагмент из базы не удаляется: он участвует в поиске режима naive, а при следующей сборке может получить сущности и связи. Поведение намеренное — для вырожденных фрагментов артефакты были бы шумом. Неудачные запросы в кэш не записываются и повторяются при каждой сборке.

Пример вызова при сборке полного графа: генеративная модель Meno и модель bge-m3 обслуживаются службой vLLM на одной машине, сервер Qdrant доступен по адресу `http://qdrant.local:6333`:

```bash
python prepare_graph_index.py -i ../data/chunked_texts_about_nsu_with_metadata_and_scores.jsonl -r ../data/chunk_mapping_to_texts.json -o ../data/knowledge/ragu_graph -e BAAI/bge-m3 --llm bond005/meno-lite-0.2 --url http://localhost:8000/v1 --key EMPTY --qdrant_location http://qdrant.local:6333 --chunk_header title --chunk_header_sources base,news -a ../data/knowledge/abbreviations.json --cache ../data/knowledge/ragu_graph_llm_cache
```

Пример вызова в режиме только векторного контекста (без генеративной модели и без сервера Qdrant):

```bash
python prepare_graph_index.py -i ../data/chunked_texts_about_nsu_with_metadata_and_scores.jsonl -r ../data/chunk_mapping_to_texts.json -o ../data/knowledge/ragu_graph_naive -e BAAI/bge-m3 --vector_only
```

Результатами построения являются файлы хранилищ RAGU в каталоге графа (`knowledge_graph.gml`, `kv_chunks.json` и другие), векторные коллекции в Qdrant и служебный файл `menon_chunk_mapping.json`, который сопоставляет идентификаторы фрагментов графа с глобальными индексами фрагментов базы знаний; по нему найденные графом фрагменты возвращаются в общий конвейер поиска «Менона».

### 3.14 Прежний сценарий автоматического индексирования

Для сборки с настраиваемой внешней LLM используйте `scripts/build_knowledge.py`
из раздела «Сборка корпуса и графа одной командой». Ниже описан прежний
`index_kb.sh`, привязанный к окружению автора, его путям и кластерным службам.

Скрипт `index_kb.sh` выполняет все шаги индексирования подряд: от разбора справочника `data/nsu_main_info.md` до построения графа знаний, включая отображение индексов из раздела 3.12. Каждый шаг пропускается, если его выходной файл уже существует; переменная окружения `FORCE=1` принудительно перезапускает шаг с перезаписью выхода. Шаг генерации метаданных при существующем выходном файле автоматически продолжается с флагом `--resume`: после обрыва долгого прогона повторный запуск обрабатывает только недостающие документы. Журналы шагов пишутся в каталог `logs` в корне репозитория. Модели, пути и адреса служб заданы переменными в начале скрипта.

Запуск выполняется из каталога `code`:

```bash
bash index_kb.sh
```

Перед запуском должны работать три службы: Qdrant, генеративная модель Meno и модель векторных представлений bge-m3. Если Qdrant по адресу `http://localhost:6333` не отвечает, скрипт сам запускает docker-контейнер `qdrant-meno` с именованным томом `qdrant_storage`. Служба векторизации bge-m3 запускается на рабочей машине скриптом `serve_local_embedder.sh` (vLLM на локальной видеокарте, порт 8001); драйвер вызывает этот скрипт сам, если служба не отвечает. Скрипт использует переменную `VLLM_BIN`: путь к исполняемому файлу `vllm`. Значение по умолчанию указывает на conda-окружение со стабильным выпуском vLLM, потому что в системном `PATH` этой машины может стоять сборка vLLM из дерева разработки, несовместимая с установленным пакетом transformers при загрузке токенизатора XLM-R (к этому семейству относится bge-m3). Если служба не поднимается с ошибкой токенизатора, задайте `VLLM_BIN` на другое окружение. Генеративная модель Meno размещается на GPU-кластере «Каскад» и пробрасывается на рабочую машину ssh-туннелем.

Задание SLURM для службы генерации лежит в `code/slurm/submit_meno_service.sh`; файл копируют на головной узел кластера и подают командой `sbatch`:

```bash
scp -i ~/nusc-nsu/nusc-nsu-key code/slurm/submit_meno_service.sh bi@11.0.1.18:/storage2/bi/
ssh -i ~/nusc-nsu/nusc-nsu-key bi@11.0.1.18 'cd /storage2/bi && sbatch submit_meno_service.sh'
```

Задание `meno-idx` обслуживает `vllm serve /storage2/bi/models/meno-lite-0.2` на порту 8000 (`--max-num-seqs 64`, `--max-model-len 16384`). Задание подаётся в партицию `a100` без закрепления за узлом, но с исключением узлов `ngpu01`, `ngpu05` и `ngpu06`: на них есть только старый стек CUDA 11.7 с окружением `vllm_env`, и его vLLM 0.7.3 падал на управляемом декодировании при извлечении артефактов (21 октября 2026 г.). Задание встаёт на первый свободный узел со свежим стеком CUDA 12.6 и окружением `actual_env` — один из узлов `ngpu02`, `ngpu03`, `ngpu04`, `ngpu07`, `ngpu08`.

Драйвер `index_kb.sh` передаёт сборщику графа флаг `--icl_examples 0`: экстракция артефактов выполняется без подстановки in-context learning примеров (few-shot, то есть с примерами в промпте). Модель meno-lite-0.2 решает задачи экстракции по схеме без примеров, а встроенные в RAGU русские примеры раздули бы каждый промпт до 15–37 тыс. токенов и не поместились бы в контекст службы. Контекст 16384 выбран с запасом: без примеров промпты стадий извлечения и валидации занимают 1,5–5 тыс. токенов. Кроме того, драйвер передаёт `-a ../data/knowledge/abbreviations.json` (расшифровка аббревиатур во фрагментах перед извлечением артефактов) и `--max_completion_tokens 6144` (потолок генерации, вмещающий списки связей фрагментов, богатых сущностями).

Задание подают сразу и держат до конца индексирования: свободные узлы кластера заполняются за часы, а извлечение сущностей и связей по полному корпусу требует многих часов непрерывной работы службы генерации. Лимит времени задания — 5 суток; ответы модели кэшируются на диске (`--cache`), поэтому после перевыдачи задания вычисление продолжается с того же места.

Проброс туннеля выполняет скрипт `open_tunnels.sh`: он определяет узел задания `meno-idx` по `squeue` и поднимает ssh-соединение с пробросом локального порта 8023 на порт 8000 этого узла. При перевыдаче задания скрипт запускают повторно.

```bash
bash open_tunnels.sh
```

После этого `index_kb.sh` находит службу генерации по адресу `http://localhost:8023/v1`, а службу векторизации — по адресу `http://localhost:8001/v1`, и ждёт готовности каждой (до 15 минут). ## 4 Как проверить работу поискового механизма на подготовленной базе знаний

### 4.1 Графовый поиск (режимы local и naive библиотеки RAGU)

Поисковый запрос обрабатывается двумя режимами RAGU, и их результаты сливаются в общий пул кандидатов:

- **local**: для запроса отбираются наиболее близкие по векторному представлению сущности, из графа извлекаются их связи, саммари сообществ и исходные фрагменты; фрагменты получают ранговые оценки, сущности — векторные оценки близости, связи — ранговые оценки;
- **naive**: гибридный поиск по фрагментам (плотный векторный поиск bge-m3 плюс лексический поиск BM25, слитые взвешиванием взаимных рангов на стороне Qdrant) с косинусными оценками.

Оценки каждого источника нормируются так, чтобы их сумма равнялась единице; объединение чанков от разных источников выполняется по максимуму оценки для каждого фрагмента. Результатом поиска служит смешанный пул из чанков, сущностей и связей; чанки отображаются в глобальные индексы базы знаний по файлу `menon_chunk_mapping.json`, а источники сущностей и связей восстанавливаются по полю `source_chunk_id` (идентификаторы фрагментов, в которых элемент графа найден).

```bash
python search_context_by_query.py -i ../data/chunked_texts_about_nsu_with_metadata_and_scores.jsonl -r ../data/chunk_mapping_to_texts.json -q "Где читает лекции профессор Иванов?" -g ../data/knowledge/ragu_graph -e BAAI/bge-m3 --graph_top_k 20 --top_k 60
```

Скрипт печатает найденные сущности с оценками, связи со своими типами, список чанков обоих режимов с глобальными индексами и оценками, а затем собранный контекст из документов и элементов графа:

```text

  [0.094] НГУ (ORG) -> chunks [40213, 1187]

```

Для изолированной проверки графового поиска служит скрипт `show_graph_search.py`: он печатает найденные сущности с оценками и списками фрагментов-источников, число связей и саммари сообществ, а также объединённый список чанков с их глобальными индексами и названиями документов:

```bash
python show_graph_search.py -g ../data/knowledge/ragu_graph -q "Где читает лекции профессор Иванов?" -e BAAI/bge-m3 --local_top_k 20 --naive_top_k 10 -i ../data/chunked_texts_about_nsu_with_metadata_and_scores.jsonl -r ../data/chunk_mapping_to_texts.json
```

Аргументы командной строки скрипта `show_graph_search.py`:

- `-g` (или `--graph`): каталог с графом знаний RAGU;
- `-q` (или `--query`): поисковый запрос;
- `-e` (или `--embedder`): имя модели векторных представлений в службе векторизации (та же модель, что использовалась при построении графа);
- `--embedder_url` и `--embedder_key`: адрес и ключ службы векторизации (если не заданы, используются `--url` и `--key`);
- `--qdrant_location`: расположение Qdrant, то же, что при сборке графа;
- `--engine_reranker`: имя модели переранжирования в службе оценки (первый проход переранжирования);
- `--local_top_k` (20): число сущностей для режима local;
- `--naive_top_k` (10): число фрагментов для режима naive;
- `-i` и `-r` (необязательные): корпус базы знаний и отображение индексов — если указаны, для каждого найденного фрагмента печатается название его документа.

### 4.2 Поиск с двухступенчатым переранжированием

Переранжирование выполняется в две ступени. Первую ступень выполняют поисковые движки RAGU: найденные фрагменты оцениваются моделью bge-reranker-v2-m3 через службу оценки (адаптер `ScorerOpenAI`), и в пуле остаются только `--engine_rerank_top_k` лучших. Первая ступень включена по умолчанию (значение `--engine_reranker` по умолчанию — `BAAI/bge-reranker-v2-m3`); пустое значение флага её отключает. Вторую ступень выполняет генеративная модель (LLM-as-reranker): каждый элемент пула (документ по своим фрагментам, сущность или связь по своему описанию) получает оценку пригодности 0, 1 или 2, итоговая оценка элемента вычисляется как взвешенная сумма его поисковой оценки и оценки переранжировщика с весом `--rerank_weight`, после чего остаются `--rerank_top_k` лучших элементов.

```bash
python search_context_by_query.py -i ../data/chunked_texts_about_nsu_with_metadata_and_scores.jsonl -r ../data/chunk_mapping_to_texts.json -a ../data/knowledge/abbreviations.json -q "Где читает лекции профессор Иванов?" -g ../data/knowledge/ragu_graph -e BAAI/bge-m3 --graph_top_k 20 --top_k 60 --engine_rerank_top_k 30 --reranker bond005/meno-tiny-0.1 --rerank_top_k 12 --min_quality 0.6 --vllm --gpu 0.85 --num_batched_tokens 1024
```

## 5 Как проверить работу различных подсистем "Менона"?

### 5.1 Проверка алгоритма текстуализации истории диалога с пользователем

Скрипт `show_dialogue_history.py` показывает, как история предшествующего диалога превращается в текст для запросов переписывания вопроса и формирования ответа. История разбивается на ходы (`TURN 1`, `TURN 2`, ...); реплика пользователя приводится полностью, ответ ассистента усекается до `--max_words` слов, факт усечения отмечается маркером `[...]`. Именно в таком виде история подставляется в запросы (образцы получившихся запросов приведены в разделе 4.2).

Входной файл имеет формат JSON: словарь, ключи которого означают типы диалогов, а значения задают списки примеров; каждый пример содержит диалог в виде последовательности сообщений с ролями `user` и `assistant`. Этому формату соответствует, например, файл `../data/fewshots/mtrageval_ru.json` с типами `How-To`, `Factoid`, `Summarization`, `Explanation`, `Keyword`, `Non-Question`, `Composite`, `Opinion`; файл хранится вне репозитория (каталог `data/fewshots` закрыт правилами `.gitignore`), генератор этого файла в репозиторий не входит.

Скрипт выбирает случайный тип диалога и случайный пример этого типа, печатает зерно генератора случайных чисел, исходный диалог и результат текстуализации. Для повторения конкретного примера задайте то же зерно флагом `-r`.

Аргументы командной строки:

- `-i` (или `--input`): входной JSON-файл с диалогами;
- `-r` (или `--random`): зерно генератора случайных чисел (без флага выбирается случайное);
- `--max_words`: предельное число слов в ответе ассистента внутри истории.

Пример вызова:

```bash
python show_dialogue_history.py -i ../data/fewshots/mtrageval_ru.json -r 42 --max_words 9
```

### 5.2 Проверка алгоритма "улучшения" пользовательского вопроса

Целью "улучшения" пользовательского вопроса является генерация одного или нескольких однозначно понимаемых без контекста поисковых запросов на основе этого вопроса. В случае, если вопрос простой, "атомарный", то он должен порождать один поисковый запрос. Синтаксически и семантически сложные вопросы могут порождать несколько поисковых запросов, разделённых символом перехода на новую строку. ### 5.3 Проверка сборки контекста из отобранных фрагментов базы знаний

Скрипт `show_context_by_chunks.py` печатает документы, которые попадают в контекст языковой модели при заданном наборе фрагментов базы знаний, и список источников к ним (названия документов с веб-ссылками). Такой просмотр полезен при оценке качества названий и аннотаций, полученных на шестом шаге конвейера.

Фрагменты задаются глобальными индексами (флаг `--chunk_idx`, повторяется для каждого индекса) или выбираются случайно (`--num_chunks`). Без обоих флагов скрипт сам выбирает от одного до четырёх случайных документов и часть их фрагментов.

Аргументы командной строки:

- `-i` (или `--input`): JSONL-файл базы знаний (результат седьмого шага);
- `-r` (или `--reverse`): JSON-файл с отображением глобальных индексов фрагментов в координаты «документ, фрагмент внутри документа»;
- `--num_chunks`: число случайно выбираемых фрагментов;
- `--chunk_idx`: глобальный индекс фрагмента; флаг повторяется для каждого индекса.

Пример вызова со случайными фрагментами:

```bash
python show_context_by_chunks.py -i ../data/chunked_texts_about_nsu_with_metadata_and_scores.jsonl -r ../data/chunk_mapping_to_texts.json --num_chunks 5
```

Пример вызова с конкретными индексами:

```bash
python show_context_by_chunks.py -i ../data/chunked_texts_about_nsu_with_metadata_and_scores.jsonl -r ../data/chunk_mapping_to_texts.json --chunk_idx 0 --chunk_idx 100 --chunk_idx 2500
```

## 6 Как запустить диалоговую систему целиком

Скрипт `chat.py` запускает интерактивный сеанс диалога с системой «Менон» в терминале. На каждый вопрос пользователя выполняются следующие действия: переписывание вопроса в один или несколько самодостаточных поисковых запросов с расшифровкой аббревиатур и учётом истории диалога; поиск по графу знаний RAGU в режимах local и naive (режим naive выполняет гибридный поиск плотными векторами и BM25 с взвешиванием взаимных рангов на стороне Qdrant); слияние результатов в общий пул из чанков, сущностей и связей; двухуровневое переранжирование пула: сначала первый проход моделью bge-reranker-v2-m3 внутри поисковых движков, затем переранжирование генеративной моделью (LLM-as-reranker) и отсечение нерелевантных элементов; формирование ответа по собранному контексту из документов и элементов графа. После ответа печатается список использованных источников.

Перед запуском должны быть доступны: служба генерации (Meno), служба векторизации (bge-m3), служба оценки (bge-reranker-v2-m3) и Qdrant с коллекциями построенного графа; служба оценки нужна из-за включённого по умолчанию первого прохода переранжирования, пустое значение `--engine_reranker` отключает его. Подготовка окружения и запуск служб описаны в разделе 2.

Пример вызова с офлайн-генерацией через vLLM:

```bash
python chat.py -i ../data/chunked_texts_about_nsu_with_metadata_and_scores.jsonl -r ../data/chunk_mapping_to_texts.json -a ../data/knowledge/abbreviations.json -o ../data/chat_output_v8.jsonl -g ../data/knowledge/ragu_graph -e BAAI/bge-m3 --qdrant_location http://qdrant.local:6333 --llm bond005/meno-lite-0.1 --vllm --gpu 0.85
```

Для генерации через внешнюю службу с OpenAI-совместимым интерфейсом уберите флаг `--vllm` и укажите адрес и ключ службы:

```bash
python chat.py -i ../data/chunked_texts_about_nsu_with_metadata_and_scores.jsonl -r ../data/chunk_mapping_to_texts.json -a ../data/knowledge/abbreviations.json -o ../data/chat_output_v8.jsonl -g ../data/knowledge/ragu_graph -e BAAI/bge-m3 --qdrant_location http://qdrant.local:6333 --llm "openai/gpt-5.4-nano" --url "https://api.vsegpt.ru/v1" --key "..."
```

Обязательные аргументы командной строки:

- `-i` (или `--input`): JSONL-файл базы знаний (результат седьмого шага конвейера);
- `-r` (или `--reverse`): JSON-файл с отображением глобальных индексов фрагментов в координаты «документ, фрагмент внутри документа»;
- `-a` (или `--abbr`): JSON-файл со словарём аббревиатур и их расшифровками;
- `-o` (или `--output`): выходной JSONL-файл; открывается в режиме добавления, поэтому для нового сеанса указывайте новый файл;
- `-g` (или `--graph`): каталог с графом знаний RAGU;
- `-e` (или `--embedder`): имя модели векторных представлений в службе векторизации (та же модель, что использовалась при построении графа);
- `--llm`: генеративная модель для переписывания вопросов, переранжирования и ответов (Meno, Qwen, Gemma и другие).

Необязательные аргументы командной строки (в скобках значения по умолчанию):

- `--max_words` (9): предельное число слов в ответе ассистента при текстуализации истории диалога;
- `--max_input_len` (4096): предельное число токенов во входе модели;
- `--max_output_len` (1024): предельное число токенов генерируемого ответа;
- `--temperature` (0.1): температура генерации;
- `--top_k` (60): число фрагментов, отбираемых режимом naive по одному переписанному запросу;
- `--graph_top_k` (20): число сущностей, отбираемых режимом local по одному запросу;
- `--engine_reranker` (`BAAI/bge-reranker-v2-m3`): имя модели переранжирования в службе оценки (первый проход двухуровневой схемы); пустое значение отключает первый проход;
- `--engine_reranker_url` и `--engine_reranker_key`: адрес и ключ службы оценки; если не заданы, используются значения `--embedder_url` и `--embedder_key`;
- `--engine_rerank_top_k` (30): число фрагментов, остающихся после первого прохода переранжирования внутри режима naive;
- `--embedder_url` и `--embedder_key`: адрес и ключ службы векторизации; если не заданы, используются значения `--url` и `--key`;
- `--qdrant_location` (пустая строка): расположение Qdrant, то же, что при сборке графа;
- `--rerank_top_k` (12): число элементов пула, остающихся после переранжирования по одному запросу;
- `--rerank_weight` (0.8): вес оценки переранжировщика в итоговой оценке элемента;
- `--min_quality` (0.0): минимальное допустимое качество документа, попадающего в контекст;
- `--gpu` (0.6): доля памяти видеокарты для офлайн-генерации через vLLM;
- `--num_batched_tokens`: предельное число токенов в одной итерации генерации через vLLM;
- `--url` (`http://localhost:8000/v1`) и `--key` (`EMPTY`): адрес и ключ внешней службы генерации.

Сведения о работе сеанса:

- сеанс завершается вводом `<end>`, `<exit>` или `<finish>` на приглашение «Задайте вопрос Менону:»;
- журнал со сведениями о поиске и генерации пишется в файл `conversation.log` текущего каталога;
- в выходной файл записываются запросы и ответы обеих ступеней (переписывание вопроса и формирование ответа) в виде JSONL-строк с полями `system`, `query`, `response`, `history`;
- записанные ранее сеансы хранятся в файлах `data/chat_output_v*.jsonl` (вне репозитория) и служат образцами вопросов и ответов системы.

## 7 Как запустить тесты

Тесты проверяют логику поискового конвейера без обращения к моделям и службам. Запуск выполняется из каталога `code` в окружении с установленными `graph_ragu` и `pytest`:

```bash
python -m pytest
```

Состав тестов:

- `tests/test_graph_utils.py` — отображение идентификаторов фрагментов графа в глобальные индексы базы знаний, нормировка оценок источников, извлечение чанков, сущностей и связей из выдачи режимов local и naive, поиск кандидатов в аббревиатуры, канонизация артефактов (регистр, пунктуация, пересборка концов связей) и этап расшифровки аббревиатур экстрактором;
- `tests/test_context_utils.py` — сборка контекста из документов, нормализация ссылок, рендеринг сущностей и связей в текстовые блоки с перечнем документов-источников, построение отображения глобальных индексов фрагментов (используется скриптом `prepare_chunk_mapping.py`);
- `tests/test_search_utils.py` — слияние списков релевантных фрагментов по максимальной оценке; адаптер службы векторизации `DenseEmbedderService` (нормализация, разбиение на мини-батчи, порядок векторов);
- `tests/test_integration_smoke.py` — пробный запуск полного поискового пути на настоящем мини-графе RAGU: сборка графа из трёх фрагментов с ручным добавлением сущности и связи, поиск по запросу, проверка отображения найденного в глобальные индексы. Тест использует Qdrant в режиме `:memory:` и детерминированную подставную модель векторных представлений, поэтому не требует ни служб, ни сети.

Медленные и интеграционные тесты помечены маркерами `slow` и `integration`; выбрать подмножество можно стандартными средствами pytest, например `python -m pytest -m "not integration"`.
